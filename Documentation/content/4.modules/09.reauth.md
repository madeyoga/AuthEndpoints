ReAuth (step-up) confirms the user's identity before sensitive mutations. It is included when you map [Identity management](/modules/identity-management) (with antiforgery in the management map).

## Schemes and header

| Piece | Value |
| --- | --- |
| Cookie scheme | `AuthEndpoints.ReAuth` (default 5 minutes, `AuthEndpointsReAuthOptions.Lifetime`) |
| Bearer scheme | `AuthEndpoints.ReAuth.Bearer` |
| Header | `X-AuthEndpoints-Reauth` with `reauthToken` |
| Policy | `ReAuthPolicy` (no authentication schemes) |

## Routes

Mapped with management. `POST /confirmIdentity` and `POST /confirmIdentity/passkeyOptions` use `AuthEndpoints.ConfirmIdentity`. `POST /confirmIdentity/emailCode/send` is mapped by `MapAccountManagementEndpoints` and `MapReAuthEndpoints` when `AddEmailCodeSendEndpoints` or `AddEmailCodeEndpoints` was called. `AddEmailCodeSignInEndpoints` alone leaves it unmapped. It uses `AuthEndpoints.ConfirmIdentity.EmailCode`. `AddPasswordAuth` adds no email-code module. `MapAccountManagementEndpoints` adds antiforgery to these `POST` routes, so send `RequestVerificationToken` on each. `MapReAuthEndpoints` adds it only when called with `requireAntiforgery: true`. Its default is `false`.

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/manage/authMethods` | Available step-up methods, including `emailCode` |
| `POST` | `/confirmIdentity` | Exactly one proof; CSRF when mapped via management |
| `POST` | `/confirmIdentity/emailCode/send` | Only with email-code send. No body. Sends a step-up code |
| `POST` | `/confirmIdentity/passkeyOptions` | WebAuthn options for passkey step-up; CSRF when mapped via management |
| `POST` | `/confirmIdentity/external/{provider}` | Only with external sign-in. Starts external step-up. Returns `{ "redirectUrl" }` |
| `GET` | `/confirmIdentity/external/{provider}/launch` | Browser navigation. Redirects to the provider |
| `GET` | `/confirmIdentity/external/{provider}/callback` | Provider return. Issues the proof, then redirects to the return URL |
| `POST` | `/confirmIdentity/external/complete` | Bearer clients. Exchanges `{ "code" }` for `{ "reauthToken" }` |

### ConfirmIdentity proof

Provide **exactly one** of:

- `password`
- `twoFactorCode`
- `twoFactorRecoveryCode`
- `credentialJson` (passkey assertion)
- `emailCode` (after `POST /confirmIdentity/emailCode/send`, when `emailCode` is true)

On success the body is `{ "reauthToken" }`. Cookie sign-ins also set `AuthEndpoints.ReAuth`. A caller authenticated with `Authorization: Bearer` (Identity bearer or JWT) gets the token only. Cookie and token share the same lifetime and both include the user's security stamp.

`emailCode` is offered only when the email-code send module is registered (`AddEmailCodeSendEndpoints` or `AddEmailCodeEndpoints`), `EmailCode.ReAuth.Enabled` is true (the default), the account email is confirmed, and the user has no password, no authenticator, and no passkey. `AddEmailCodeSignInEndpoints` alone does not offer it. An external login does not hide the proof.

That send route has no body. It requires the signed-in user and a CSRF token when management mapped it. The rate limit is `AuthEndpoints.ConfirmIdentity.EmailCode` (3 requests per minute per user). The `200` body is `{ "expiresInSeconds", "resendAfterSeconds" }`. The code lasts `EmailCode.ReAuth.CodeLifetime` (default 5 minutes, 1 through 10). It is single use. A security-stamp change invalidates it. The message purpose is `ReAuth` (`2`) and `LinkUrl` is null. Cooldown and the per-address send cap are separate from sign-in codes. A wrong code counts toward lockout when `CountFailuresTowardLockout` is true. Five wrong attempts is the default cap.

### External provider step-up

When the host registers external sign-in (`AddExternalAuthEndpoints`), a user can confirm their identity by signing in again at a provider they already linked. This lets an external-only account with no password, passkey, authenticator, or email code add one of those. External step-up is **on by default**.

`GET /manage/authMethods` gains `external: [{ "scheme", "displayName" }]`. It lists linked providers that are registered and allowed. Every other field is unchanged.

Flow:

1. `POST /confirmIdentity/external/{provider}` with an optional `{ "returnUrl" }`. It requires the signed-in user, plus antiforgery when management mapped it. The provider must be linked to the user. The response is `{ "redirectUrl" }`.
2. Navigate the browser to `redirectUrl`. It carries one-time state, protected with data protection. The state holds the user id, provider, nonce, start time, the validated return URL, and the security stamp. It expires after `ReAuth.External.RequestLifetime` (default 5 minutes, 1 through 30).
3. The provider is asked for a fresh sign-in where it supports one. OpenID Connect schemes get `prompt=login` and `max_age=0`. A provider can implement `IExternalReAuthChallenge` to set its own parameters. GitHub and Google get no extra parameters.
4. The callback accepts only valid, unexpired, single-use state. The returned login must already belong to the same user and the security stamp must be unchanged. When the provider returns `auth_time`, it must not predate the start. Rejections redirect to `ExternalAuthOptions.ErrorPath` with `error` set to `invalid_request`, `login_not_linked`, `user_mismatch`, or `stale_sign_in` (or return problem JSON to JSON clients).
5. Cookie sessions get the `AuthEndpoints.ReAuth` cookie and land on the return URL. Bearer clients land on the return URL with a one-time `reauthCode` query value. Exchange it at `POST /confirmIdentity/external/complete` with the same bearer token. The code lasts 2 minutes and is single use. The `reauthToken` is only ever in a response body, never in a URL.

The callback never signs anyone in, never links a login, never creates a session, and never accepts provider tokens posted by the client. It requires the same signed-in session that started the request. All four routes use the `AuthEndpoints.ConfirmIdentity` rate limit, and each step is logged under `AuthEndpoints.ExternalReAuth`.

Opt out globally or per provider:

```csharp
builder.Services.Configure<AuthEndpointsReAuthOptions>(reauth =>
{
    reauth.External.Enabled = false;              // all providers
    reauth.External.DisabledProviders.Add("GitHub"); // one provider
});
```

::callout{icon="i-lucide-triangle-alert" color="warning"}
External step-up proves the user controls the provider session right now. That is weaker than a password or passkey. A provider may ignore `prompt=login` and return without asking for credentials, so the proof is only as strong as the provider's own session policy. Turn it off for providers you do not trust for sensitive changes. The single-use ledger is in memory, so in a multi-instance deployment a state or code could be replayed on another instance within its short lifetime.
::

The step-up credential is an extra proof on top of a sign-in. It is never a sign-in by itself, and it never replaces `HttpContext.User`. `ReAuthPolicy` adds no authentication schemes. The requirement looks at the user the route already authenticated, then authenticates the ReAuth cookie and `X-AuthEndpoints-Reauth`. It succeeds only when that proof has `Reauth=true`, the same user id, and, when the store supports security stamps, the user's current security stamp. A missing stamp claim is rejected. A password change, reset, or `UpdateSecurityStampAsync` cancels outstanding cookies and tokens. A request with only the cookie or the header is rejected (`401` or `403`). A signed-in user with no proof, an expired proof, a proof issued to someone else, or a stale stamp gets `403`.

Pair `.RequireReauth()` with `.RequireAuthorization()` that signs the user in. Account management, passkey mutations, and external unlink use the registered application-cookie, Identity bearer, and JWT bearer schemes. `.RequireReauth()` alone does not authenticate those schemes. A route that omits the sign-in authorization fails.

## Lifetime

Default is **5 minutes**, non-persistent, no sliding expiration. Set `AuthEndpointsReAuthOptions.Lifetime` (a `TimeSpan`) with `Configure<AuthEndpointsReAuthOptions>`. The password facade and a composed host read the same options. One value drives confirm `ExpiresUtc`, cookie `ExpireTimeSpan`, and `reauthToken` expiry.

Valid range: 1 minute through 60 minutes. Startup rejects zero, negative, over 60 minutes, and `InfiniteTimeSpan`.

```cs
builder.Services.AddPasswordAuth<AppUser, AppDbContext>();
builder.Services.Configure<AuthEndpointsReAuthOptions>(o =>
{
    o.Lifetime = TimeSpan.FromMinutes(2);
});
```

## Protecting host endpoints

```cs
builder.Services.AddCookieAuthEndpoints(); // or AddBearerAuthEndpoints. Both register the ReAuth schemes.

app.MapPost("/billing/update", handler)
    .RequireAuthorization() // list the sign-in schemes this route accepts
    .RequireReauth();
```

`.RequireAuthorization()` without schemes uses the host default sign-in. Pass the Identity bearer and JWT schemes when those tokens should count, the same way management routes do. A signed-in caller without a matching proof gets `403`.

## Typical client flow

The steps use the password facade prefix `/auth`.

1. `GET /auth/manage/authMethods`
2. Collect proof: password, 2FA, a passkey via `POST /auth/confirmIdentity/passkeyOptions`, a linked provider via `POST /auth/confirmIdentity/external/{provider}`, or `emailCode` via `POST /auth/confirmIdentity/emailCode/send`. The send route exists only when the host adds email-code send (`AddEmailCodeSendEndpoints` or `AddEmailCodeEndpoints`). `AddEmailCodeSignInEndpoints` alone leaves it unmapped.
3. `POST /auth/confirmIdentity` with CSRF
4. Retry the sensitive action with ReAuth cookie and/or `X-AuthEndpoints-Reauth`

## Where ReAuth is required

- Manage 2FA, info, and set-password mutations
- Passkey add, rename, delete, and creation options
- External OAuth unlink
- Any host endpoint with `.RequireReauth()`
