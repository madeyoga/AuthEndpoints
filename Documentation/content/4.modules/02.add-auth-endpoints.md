`AddAuthEndpoints<TUser, TContext>()` returns a builder. Each `Add*` on the builder turns on one sign-in method or session. `MapAuthEndpoints<TUser>(path, session)` maps exactly what was added, under one prefix, so registration and mapping cannot disagree. The builder adds no routes of its own. It expands to the building-block calls on this page.

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>()
    .AddPassword()
    .AddPasskeys(passkeys => passkeys.ServerDomain = "example.com")
    .AddEmailCode();

app.UseAuthEndpoints();
app.MapAuthEndpoints<AppUser>("/auth", AuthEndpointsSession.Cookie);
```

`TUser` is a `class` with a public parameterless constructor. `TContext` is a `DbContext`. `AddAuthEndpoints<TUser, TRole, TContext>()` registers roles before the EF stores. `TRole` is a `class`, and that context is `IdentityDbContext<TUser, TRole, TKey>` or the equivalent. `MapAuthEndpoints` without `AddAuthEndpoints` throws `InvalidOperationException` with `Call AddAuthEndpoints before MapAuthEndpoints.`

The tutorial is the [quick start](/getting-started/quick-start). Options are in [Configuration options](/modules/configuration#authendpointsoptions). Routes for each `Add*` and `Map*` pair are in the [composition table](/modules/composition).

## What AddAuthEndpoints registers

Without any builder call, `AddAuthEndpoints` registers Identity with EF stores, the cookie session, and account management (`/manage/info`, `/manage/2fa`, `/manage/authMethods`, `/manage/password`, `/confirmIdentity`, and confirm-email). `RequireConfirmedAccount` defaults to `true`.

The optional callback configures `AuthEndpointsOptions`: the confirm-email redirect and the Production email-sender check. A later `Configure<AuthEndpointsOptions>` applies too.

## Builder methods

| Method | Adds | Options |
| --- | --- | --- |
| `AddPassword()` | Password sign-in. By default also sign-up and recovery. | `PasswordFeatureOptions`: `SignUp` (default `true`), `Recovery` (default `true`) |
| `AddPasskeys()` | Passkey sign-in, and step-up with a passkey. By default also anonymous passkey sign-up and passkey management. | `PasskeyFeatureOptions`: `ServerDomain`, `SignUp` (default `true`), `Management` (default `true`) |
| `AddEmailCode()` | Email-code send and sign-in, and step-up with an email code for a passwordless account. | `EmailCodeOptions` ([Email code](/modules/email-code)) |
| `AddJwt(configure)` | The JWT session. Required before mapping `AuthEndpointsSession.Jwt`. A missing signing key throws while the host is being built. | `SimpleJwtOptions` ([JWT](/modules/jwt#options)) |
| `AddIdentityBearer()` | The Identity bearer session. Required before mapping `AuthEndpointsSession.IdentityBearer`. | none |
| `ConfigureIdentity(configure)` | Identity options, such as `SignIn.RequireConfirmedAccount` and password rules. | `IdentityOptions` |

Calling a method twice adds the union of both calls. `Services` and `Identity` on the builder expose the service collection and the `IdentityBuilder` for anything else.

## Sessions

`MapAuthEndpoints` takes one session.

- `AuthEndpointsSession.Cookie` maps `POST /login`, `POST /logout`, and `GET /csrfToken`. Password sign-in does not use antiforgery. `GET /csrfToken` issues the token for logout, manage `POST` routes, and step-up.
- `AuthEndpointsSession.Jwt` maps `POST /create`, `POST /refresh`, `GET /verify`, and `POST /logout`. Cookie refresh also maps `GET /csrfToken`. Body refresh omits that route. The `DbContext` calls `UseRefreshToken()`, and you add a migration before production.
- `AuthEndpointsSession.IdentityBearer` maps `POST /login`, `POST /refresh`, and `POST /logout`, and no `GET /csrfToken`.

Mapping `Jwt` without `AddJwt` throws `Call AddJwt on AddAuthEndpoints before MapAuthEndpoints with AuthEndpointsSession.Jwt.` Mapping `IdentityBearer` without `AddIdentityBearer` throws the same way.

Passkey ceremonies, `POST /passkeys/register/options` included, follow the session. Cookie and JWT cookie refresh require a CSRF token on them. Identity bearer and JWT body refresh do not. Management routes keep antiforgery.

For more than one session, map each session's sign-in with `MapSignInEndpoints` on its own prefix, and the shared routes once with `MapSharedAuthEndpoints`. See [Composition](/modules/composition#per-session-and-shared-routes). Calling `MapAuthEndpoints` twice maps the shared routes twice and logs a warning.

## What the map includes

`MapAuthEndpoints` calls `MapSignInEndpoints<TUser>(session)` and the shared map on one group, and returns that group, so `WithTags` and other conventions apply to every route.

- Password: `POST /register` when sign-up is on, the session's sign-in route, and `POST /forgotPassword` and `POST /resetPassword` when recovery is on.
- Passkeys: `POST /passkeys/requestOptions` and `POST /passkeys/login`, `POST /passkeys/register/options` and `POST /passkeys/register` when sign-up is on, management under `/passkeys/` when management is on, and `POST /confirmIdentity/passkeyOptions`.
- Email code: `POST /emailCode/send`, `POST /emailCode/verify`, and `POST /confirmIdentity/emailCode/send`.
- Always: the session routes, confirm-email and resend, and account management.

Each feature you leave out logs one `Skipped …` line at startup, naming its routes and the builder call that adds them. See [Skipped routes](/modules/composition#skipped-routes).

External sign-in is not part of the builder. Map it beside the builder with `AddExternalAuthEndpoints` and `MapExternalAuthEndpoints`. See [External OAuth](/modules/external-oauth).

The builder registers the individual password features, not the `AddPasswordEndpoints` bundle. An extra `MapCookieAuthEndpoints` throws `InvalidOperationException` with `Call AddPasswordEndpoints before MapCookieAuthEndpoints.` An extra `MapIdentityManagementApi` throws `Call AddPasswordEndpoints before MapPasswordEndpoints.` The throw happens when the map runs.

## Building-block expansion

`AddAuthEndpoints().AddPassword().AddPasskeys()` and `MapAuthEndpoints` expand to these calls. Copy them when you need finer control. `AddAuthEndpoints<TUser, TRole, TContext>` uses the same list and calls `AddRoles<TRole>()` before `AddEntityFrameworkStores<TContext>()`.

```cs
services.AddAuthEndpointsIdentity<TUser, TContext>();
services.AddCookieSessionEndpoints();
services.AddAccountManagementEndpoints();

// AddPassword():
services.AddPasswordSignInEndpoints();
services.AddPasswordSignUpEndpoints();     // SignUp
services.AddPasswordRecoveryEndpoints();   // Recovery

// AddPasskeys(p => p.ServerDomain = domain):
services.AddPasskeySignInEndpoints<TUser>();
services.AddPasskeySignUpEndpoints<TUser>();          // SignUp
services.AddPasskeyRegisterOptionsEndpoints();        // SignUp
services.AddPasskeyManagementEndpoints();             // Management
services.Configure<IdentityPasskeyOptions>(passkeys => passkeys.ServerDomain = domain);

// AddEmailCode(configure):
services.AddEmailCodeEndpoints<TUser, TContext>(configure);

// AddJwt(configure):
services.AddJwtEndpoints<TUser, TContext>(configure);

// AddIdentityBearer():
services.AddBearerSessionEndpoints();
```

Map under one group:

```cs
var group = app.MapGroup("/auth");
group.MapSignInEndpoints<TUser>(session);
group.MapSharedAuthEndpoints<TUser>();
```

One difference: `MapSharedAuthEndpoints` serves every session, so it always requires a CSRF token on `POST /passkeys/register/options`. `MapAuthEndpoints` maps one session, so that route follows the session like the other ceremonies.
