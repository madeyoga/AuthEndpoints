Passkey (WebAuthn) endpoints for passwordless register/login and managing credentials on an existing account.

## DI

```cs
builder.Services.AddPasskeyEndpoints<AppUser>();
```

This registers passkey rate limits/ReAuth and the default `IdentityPasskeySignInCompleter<AppUser>`. Prefer the generic overload for compose hosts so register/login can resolve `IPasskeySignInCompleter<TUser>`.

To choose the user id minted during passwordless register:

```cs
builder.Services.AddPasskeyUserIdFactory(() => Ulid.NewUlid().ToString());
```

Or register an `IPasskeyUserIdFactory` implementation. When no custom factory is registered, the id is `Guid.NewGuid()` (UUID v4).

On the password facade, passkeys stay off until `Passkeys.ServerDomain` is set. On the 3.x facade, passkeys are on until `Passkeys.Enabled` is `false`, and Production requires `ServerDomain` while they are on.

## Map

```cs
app.MapGroup("/account").MapPasskeyEndpoints<AppUser>();
```

Routes are mapped under `{prefix}/passkeys` (facade default `/account/passkeys`).

Sign-in and credential management can be mapped on their own:

```cs
app.MapGroup("/account").MapPasskeySignInEndpoints<AppUser>();
app.MapGroup("/account").MapPasskeyManagementEndpoints<AppUser>();
```

To finish register and login with a built-in session, pass `AuthEndpointsSession`: `MapPasskeySignInEndpoints<AppUser>(AuthEndpointsSession.Jwt)`. A single string is the confirm-email endpoint name, not a completer. When that string matches a registered completer name, the map logs a warning and still uses the default completer.

`AddPasskeyEndpoints` also registers the password, cookie-session, and account-management modules. A host that calls only `AddPasskeyEndpoints`, then `MapIdentityManagementApi` and `MapCookieAuthEndpoints`, does not fail the missing-`Add*` check for those maps. A missing `Add*` throws `InvalidOperationException` when the map runs. The message is `Call {Add} before {Map}.`

`AddPasskeyEndpoints` registers every passkey module. `AddPasskeySignInEndpoints`, `AddPasskeySignUpEndpoints`, `AddPasskeyRegisterOptionsEndpoints`, and `AddPasskeyManagementEndpoints` register one each.

`MapPasskeySignInEndpoints` maps `requestOptions`, `register/options`, `register`, and `login` under `/passkeys`. `POST /passkeys/register` creates an account. The method also maps `GET /confirmEmail` and `POST /resendConfirmationEmail` on the parent group when that endpoint name is new.

Passkey login without that register route uses `MapSignInEndpoints`. Call `AddPasskeySignInEndpoints` and do not call `AddPasskeyEndpoints` or `AddPasskeySignUpEndpoints`. Those two register sign-up, and `MapSignInEndpoints` then maps `POST /passkeys/register` as well. `MapPasskeySignInEndpoints` always maps register, even when only `AddPasskeySignInEndpoints` was called.

`MapPasskeyManagementEndpoints` maps `creationOptions`, `POST /`, `GET /`, `PATCH /`, and `DELETE /{credentialIdUrl}` under `/passkeys`. `MapPasskeyEndpoints` maps sign-in and management on one `/passkeys` group and leaves confirm-email to the caller. Passwordless register can keep using `AuthEndpointsEndpointNames.ConfirmEmail<TUser>()`. Map `MapConfirmEmailEndpoints` or `MapAccountManagementEndpoints` with that name. The user store still has to support passkeys and email.

## Routes

| Method | Path | Auth / extras |
| --- | --- | --- |
| `POST` | `/passkeys/creationOptions` | Signed-in + ReAuth + CSRF filter + rate limit |
| `POST` | `/passkeys/requestOptions` | CSRF + rate limit; optional body `{ email }` |
| `POST` | `/passkeys/register/options` | CSRF; body `{ email }` |
| `POST` | `/passkeys/register` | CSRF; passwordless create + completer sign-in |
| `POST` | `/passkeys/login` | CSRF; completer sign-in (`useCookies` / `useSessionCookies` for Identity completer) |
| `POST` | `/passkeys/` | Add passkey (signed-in + ReAuth + CSRF filter) |
| `GET` | `/passkeys/` | List passkeys (signed-in) |
| `PATCH` | `/passkeys/` | Rename (signed-in + ReAuth + CSRF filter). Name is trimmed, max 200. |
| `DELETE` | `/passkeys/{credentialIdUrl}` | Remove (signed-in + ReAuth + CSRF filter). Refuses the last sign-in method. |

Identifier-first `requestOptions` with `email` may reveal passkey presence via `allowCredentials`. Omit `email` for usernameless/discoverable login.

## Passwordless register flow

1. `POST /account/passkeys/register/options` with `{ "email": "..." }`
2. Browser `navigator.credentials.create(...)`
3. `POST /account/passkeys/register` with `{ "email": "...", "credentialJson": "..." }`

A successful **user create** sends the same confirmation email as password `POST /register`. The account is not marked confirmed. Completers still skip a session when `CanSignInAsync` fails (for example `RequireConfirmedAccount`). Duplicate-email and failed-attestation paths do not send that mail. Passwordless register never attaches a passkey to an existing user id; add a credential to an existing account with authenticated `POST /passkeys/creationOptions` then `POST /passkeys/`.

Client steps for passkey registration: [Register users](/guides/registration#register-with-a-passkey).

## Sign-in completer

After a successful register/login ceremony, the library runs lockout and `CanSignInAsync`. It calls `IPasskeySignInCompleter<TUser>` only when sign-in is allowed.

::callout{icon="i-lucide-triangle-alert" color="warning"}
Passkey sign-in skips two-factor authentication. The Identity bearer completer and the JWT completer both issue a session with no 2FA check. A user who turned on 2FA can still sign in with a passkey alone. A passkey is a phishing-resistant first factor. If the app needs a second factor after a passkey, register a completer that checks it.
::

### Default: Identity

`IdentityPasskeySignInCompleter` honors the same query flags as Identity bearer `Login` (`MapBearerAuthEndpoints`):

- `?useCookies=true` → persistent application cookie
- `?useSessionCookies=true` → session application cookie
- neither → Identity bearer token (`AccessTokenResponse`)

::callout{icon="i-lucide-info"}
The default completer follows bearer `Login` flags, **not** facade `LoginCookie`. `?useCookies=true` has no effect on `POST /identity/login` under `MapAuthEndpoints`. See [Cookie auth](/modules/cookie-auth).
::

Passwordless register returns one body:

- Cookie sign-in (`useCookies` or `useSessionCookies`) returns `PasskeyCredentialResponse` (`credentialId`; `displayName` and `createdAt` when present) and sets the application cookie.
- Bearer sign-in returns `AccessTokenResponse`. `SignInAsync` already wrote that body, so the response does not also include `credentialId`.
- When sign-in is not allowed, register returns that credential id and does not issue a session or tokens.

Login returns `401` Invalid credentials when sign-in is not allowed. A custom completer cannot issue a cookie or token on those paths.

List and add return the same shape. `POST /passkeys/` and `PATCH /passkeys/` accept a name (trimmed, max 200). Identity stores that as `UserPasskeyInfo.Name`. JSON still uses `displayName`. A rename longer than 200 characters returns a validation problem `Name`.

When the library gate denies sign-in (unconfirmed account, lockout):

| Kind | Response |
| --- | --- |
| Register | `PasskeyCredentialResponse` (credential id); **no** session or tokens |
| Login | `401` Invalid credentials |

### Simple JWT

Pass `AuthEndpointsSession.Jwt` to `MapPasskeySignInEndpoints`. That session needs `AddJwtEndpoints`:

```cs
builder.Services.AddPasskeyEndpoints<AppUser>();
builder.Services.AddJwtEndpoints<AppUser, AppDbContext>(o =>
{
    o.Issuer = "https://example.com";
    o.Audience = "https://example.com";
    o.SigningOptions.SymmetricKey = builder.Configuration["Jwt:SymmetricKey"];
});

app.MapGroup("/account").MapPasskeySignInEndpoints<AppUser>(AuthEndpointsSession.Jwt);
```

Successful passkey register and login return the same shape as JWT `/create`: access token in JSON and the HttpOnly refresh cookie. The body does not include `credentialId`. Cookie query flags are ignored.

`Jwt.Enabled` on the 3.x facade does not select this session. `AddPasskeySignInCompleter` and `JwtPasskeySignInCompleter<TUser>` are obsolete. They still run when the map passes no session. See [Upgrade to 4.0](/guides/upgrading-to-4).

Signed-in routes accept the application cookie, Identity bearer, and JWT bearer schemes that the host registered (the same set as account management). A ReAuth cookie or `X-AuthEndpoints-Reauth` token is not a sign-in. `GET /passkeys/` returns `401` until one of those sign-in schemes authenticates. Mutations also require ReAuth for that same user, so a signed-in caller without a matching step-up proof gets `403`.

The CSRF filter on signed-in changes runs the [usual skip rule](/modules/csrf). A cookie session must send a CSRF token. An `Authorization: Bearer` access token skips the check. A token the host reads from a cookie, with no `Authorization` header, still needs a CSRF token.

## Constraints

- Passwordless register needs `IdentityUser` with `string` or `Guid` key. The default user id is `Guid.NewGuid()` (UUID v4). Apps can override the minted id by registering `IPasskeyUserIdFactory`.
- `MapPasskeyEndpoints` throws at map time if the user store lacks passkey or email support. The module is email-keyed.
- Anonymous ceremonies (`requestOptions`, `register/options`, `register`, `login`) always require CSRF. They store the WebAuthn challenge in the `Identity.TwoFactorUserId` cookie and read it back to finish the ceremony. `register` and `login` can also set an application cookie when `useCookies` or `useSessionCookies` is true. The bearer facade does not map a token route, so a bearer host that maps passkeys maps its own.
- `DELETE /passkeys/{credentialIdUrl}` returns a validation problem `LastSignInMethod` when the passkey is the only sign-in method (no password and no external login). Two-factor authentication does not count.
- Sensitive credential mutations require ReAuth.
