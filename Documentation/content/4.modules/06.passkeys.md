Passkey (WebAuthn) endpoints for passwordless register/login and managing credentials on an existing account.

## DI

```cs
builder.Services.AddPasskeyEndpoints<AppUser>();
```

This registers passkey rate limits/ReAuth and the default `IdentityPasskeySignInCompleter<AppUser>`. Prefer the generic overload for compose hosts so register/login can resolve `IPasskeySignInCompleter<TUser>`.

To choose the user id minted during passwordless register:

```cs
builder.Services.AddPasskeyUserIdFactory(() => Ulid.NewUlid().ToString());
```

Or register an `IPasskeyUserIdFactory` implementation. When no custom factory is registered, the id is `Guid.NewGuid()` (UUID v4).

Facade: passkeys are **enabled by default**; set `Passkeys.ServerDomain` (required in Production).

## Map

```cs
app.MapGroup("/account").MapPasskeyEndpoints<AppUser>();
```

Routes are mapped under `{prefix}/passkeys` (facade default `/account/passkeys`).

## Routes

| Method | Path | Auth / extras |
| --- | --- | --- |
| `POST` | `/passkeys/creationOptions` | Signed-in + ReAuth + CSRF filter + rate limit |
| `POST` | `/passkeys/requestOptions` | CSRF + rate limit; optional body `{ email }` |
| `POST` | `/passkeys/register/options` | CSRF; body `{ email }` |
| `POST` | `/passkeys/register` | CSRF; passwordless create + completer sign-in |
| `POST` | `/passkeys/login` | CSRF; completer sign-in (`useCookies` / `useSessionCookies` for Identity completer) |
| `POST` | `/passkeys/` | Add passkey (signed-in + ReAuth + CSRF filter) |
| `GET` | `/passkeys/` | List passkeys (signed-in) |
| `PATCH` | `/passkeys/` | Rename (signed-in + ReAuth + CSRF filter). Name is trimmed, max 200. |
| `DELETE` | `/passkeys/{credentialIdUrl}` | Remove (signed-in + ReAuth + CSRF filter). Refuses the last sign-in method. |

Identifier-first `requestOptions` with `email` may reveal passkey presence via `allowCredentials`. Omit `email` for usernameless/discoverable login.

## Passwordless register flow

1. `POST /account/passkeys/register/options` with `{ "email": "..." }`
2. Browser `navigator.credentials.create(...)`
3. `POST /account/passkeys/register` with `{ "email": "...", "credentialJson": "..." }`

A successful **user create** sends the same confirmation email as password `POST /register`. The account is not marked confirmed. Completers still skip a session when `CanSignInAsync` fails (for example `RequireConfirmedAccount`). Duplicate-email and failed-attestation paths do not send that mail. Passwordless register never attaches a passkey to an existing user id; add a credential to an existing account with authenticated `POST /passkeys/creationOptions` then `POST /passkeys/`.

Client steps for passkey registration: [Register users](/guides/registration#register-with-a-passkey).

## Sign-in completer

After a successful register/login ceremony, the library runs lockout and `CanSignInAsync`. It calls `IPasskeySignInCompleter<TUser>` only when sign-in is allowed.

::callout{icon="i-lucide-triangle-alert" color="warning"}
Passkey sign-in skips two-factor authentication. `IdentityPasskeySignInCompleter` calls `SignInAsync` directly, and `JwtPasskeySignInCompleter` issues tokens without a 2FA check. A user who turned on 2FA can still sign in with a passkey alone. A passkey is a phishing-resistant first factor. If your app needs a second factor after a passkey, register a completer that checks it.
::

### Default: Identity

`IdentityPasskeySignInCompleter` honors the same query flags as Identity bearer `Login` (`MapBearerAuthEndpoints`):

- `?useCookies=true` → persistent application cookie
- `?useSessionCookies=true` → session application cookie
- neither → Identity bearer token (`AccessTokenResponse`)

::callout{icon="i-lucide-info"}
The default completer follows bearer `Login` flags, **not** facade `LoginCookie`. `?useCookies=true` has no effect on `POST /identity/login` under `MapAuthEndpoints`. See [Cookie auth](/modules/cookie-auth).
::

Register also returns `PasskeyCredentialResponse` (`credentialId`; `displayName` and `createdAt` when present). If sign-in is not allowed, register still returns that credential id with no session. Login returns `401` Invalid credentials. A custom completer cannot issue a cookie or token on those paths.

List and add return the same shape. `POST /passkeys/` and `PATCH /passkeys/` accept a name (trimmed, max 200). Identity stores that as `UserPasskeyInfo.Name`. JSON still uses `displayName`. A rename longer than 200 characters returns a validation problem `Name`.

When the library gate denies sign-in (unconfirmed account, lockout):

| Kind | Response |
| --- | --- |
| Register | `PasskeyCredentialResponse` (credential id); **no** session or tokens |
| Login | `401` Invalid credentials |

### Simple JWT

Register `JwtPasskeySignInCompleter` instead (requires `AddJwtEndpoints`):

```cs
builder.Services.AddPasskeyEndpoints<AppUser>();
builder.Services.AddJwtEndpoints<AppUser, AppDbContext>(o =>
{
    o.Issuer = "https://example.com";
    o.Audience = "https://example.com";
    o.SigningOptions.SymmetricKey = builder.Configuration["Jwt:SymmetricKey"];
});
builder.Services.AddPasskeySignInCompleter<AppUser, JwtPasskeySignInCompleter<AppUser>>();
```

Successful passkey register/login then returns the same shape as JWT `/create`: access token in JSON + HttpOnly refresh cookie. Cookie query flags are ignored for this completer.

Facade JWT opt-in does **not** auto-select the JWT completer — register it explicitly when you want Simple JWT after passkeys.

Signed-in routes accept the application cookie, Identity bearer, and JWT bearer schemes that the host registered (the same set as account management). A ReAuth principal alone is not enough. `GET /passkeys/` returns `401` until one of those sign-in schemes authenticates. Mutations also require ReAuth, so a signed-in caller without step-up gets `403`.

The CSRF filter on signed-in changes runs the [usual skip rule](/modules/csrf). A cookie session must send a CSRF token. An `Authorization: Bearer` access token skips the check unless `OnMessageReceived` reads that token from a cookie.

## Constraints

- Passwordless register needs `IdentityUser` with `string` or `Guid` key. The default user id is `Guid.NewGuid()` (UUID v4). Apps can override the minted id by registering `IPasskeyUserIdFactory`.
- `MapPasskeyEndpoints` throws at map time if the user store lacks passkey or email support. The module is email-keyed.
- Anonymous ceremonies (`requestOptions`, `register/options`, `register`, `login`) always require CSRF. They store the WebAuthn challenge in the `Identity.TwoFactorUserId` cookie and read it back to finish the ceremony. `register` and `login` can also set an application cookie when `useCookies` or `useSessionCookies` is true. The bearer facade does not map a token route, so a bearer host that maps passkeys maps its own.
- `DELETE /passkeys/{credentialIdUrl}` returns a validation problem `LastSignInMethod` when the passkey is the only sign-in method (no password and no external login). Two-factor authentication does not count.
- Sensitive credential mutations require ReAuth.
