`AddAuthEndpoints<TUser>(…)` takes `AuthEndpointsOptions`. Each builder method takes its own options. The modules it registers read their own options: `SimpleJwtOptions`, `EmailCodeOptions`, `IdentityPasskeyOptions`, and `AuthEndpointsReAuthOptions`.

## AuthEndpointsOptions

Runtime settings shared by every route. `AddAuthEndpoints` configures it, and a later `Configure<AuthEndpointsOptions>` applies too. A composed host sets it with `Configure<AuthEndpointsOptions>`. The building-block expansion is on [AddAuthEndpoints](/modules/add-auth-endpoints). Routes are in the [composition table](/modules/composition).

| Property | Default | Description |
| --- | --- | --- |
| `EmailConfirmation` | (unset) | `ConfirmEmailRedirectUri` and `AllowedRedirectOrigins`. See [Email confirmation](#email-confirmation). |
| `RequireEmailSenderInProduction` | `true` | With `AddAuthEndpoints`, Production must register a real `IEmailSender<TUser>` |

Identity options, such as `SignIn.RequireConfirmedAccount` (default `true`) and password rules, are set with `.ConfigureIdentity(...)` on the builder, or `Configure<IdentityOptions>`.

## Builder options

`AddPassword` takes `PasswordFeatureOptions`:

| Property | Default | Description |
| --- | --- | --- |
| `SignUp` | `true` | Maps `POST /register` |
| `Recovery` | `true` | Maps `POST /forgotPassword` and `POST /resetPassword` |

`AddPasskeys` takes `PasskeyFeatureOptions`:

| Property | Default | Description |
| --- | --- | --- |
| `ServerDomain` | `null` | WebAuthn relying-party domain (e.g. `example.com`). Copied onto `IdentityPasskeyOptions.ServerDomain`. |
| `SignUp` | `true` | Maps anonymous passkey sign-up: `POST /passkeys/register/options` and `POST /passkeys/register` |
| `Management` | `true` | Maps listing, adding, renaming, and removing a signed-in user's passkeys |

`AddEmailCode` takes `EmailCodeOptions` ([Email code](#email-code)). `AddJwt` takes `SimpleJwtOptions` ([JWT](#jwt)).

## Passkeys

A composed host that calls `AddPasskeyEndpoints<TUser>()` sets `IdentityPasskeyOptions.ServerDomain` with `Configure<IdentityPasskeyOptions>`.

Passkey ceremonies require an antiforgery token for a cookie session and for JWT cookie refresh. On `MapAuthEndpoints` with Identity bearer, or with JWT and body refresh transport, no `GET /csrfToken` is mapped and those ceremonies do not require a token. See [Passkeys with JWT body transport](/modules/passkeys#jwt-body-transport).

## Email confirmation

`AuthEndpointsOptions.EmailConfirmation`, which the confirm-email handler reads. Set it in the `AddAuthEndpoints` callback, or with `Configure<AuthEndpointsOptions>` on a composed host.

| Property | Default | Description |
| --- | --- | --- |
| `ConfirmEmailRedirectUri` | `null` | After browser `GET` confirm-email, redirect here instead of the plain-text / 401 response. Absolute `https://` (or `http://` in Development), or a rooted path such as `/auth/email-confirmed`. |
| `AllowedRedirectOrigins` | empty | Origins such as `https://app.example.com` required when the redirect URI is absolute. A rooted path does not need an entry. |

URI rules:

- Protocol-relative (`//…`) and non-http(s) schemes are rejected.
- A rooted path is resolved against the request public origin (`scheme://host`, including port). `PathBase` is not included.
- An absolute URI must match an allowlist entry on scheme, host, and optional port (origin only).
- Absolute URI plus an empty allowlist is refused.
- Absolute `http://` is refused unless the host is Development.

With `AddAuthEndpoints`, startup validation also checks the value:

- A protocol-relative URI or a non-http(s) scheme fails startup in every environment.
- In Production, an absolute `http://` URI, an absolute URI with an empty allowlist, and an absolute URI whose origin is not on the allowlist fail startup.

A composed host that does not call `AddAuthEndpoints` has no startup check. The confirm-email handler checks the redirect on each request. When the value is refused, confirm-email does not redirect. Success returns `200` with plain text, and failure returns `401`.

Every redirect overwrites (does not append) these query parameters:

| Name | Values |
| --- | --- |
| `status` | `confirmed` or `failed` |
| `flow` | `confirm` when `changedEmail` is absent; `change-email` when it is present |

The redirect query does not include tokens, user ids, or emails.

Client steps for sign-up with email confirmation: [Register users](/guides/registration).

## JWT

`.AddJwt(jwt => …)` takes an `Action<SimpleJwtOptions>`. It is required before mapping `AuthEndpointsSession.Jwt`. A composed host passes the same callback to `AddJwtEndpoints<TUser>(…)`.

`SimpleJwtOptions` holds every JWT setting, including the refresh session: `RefreshTokenTransport` (default `Cookie`), `RefreshTokenLifetime`, and `AbsoluteLifetime`. Set them in the `AddJwt` or `AddJwtEndpoints` callback. They are fixed when that call runs, so `Configure<SimpleJwtOptions>` afterwards has no effect.

### SimpleJwtOptions

Common settings:

| Property | Notes |
| --- | --- |
| `Issuer` / `Audience` | Production rejects the library defaults (`Jwt` / `JwtAudience`) |
| `AccessTokenLifetime` | Default 15 minutes |
| `SigningOptions` | Symmetric (key ≥ 32 UTF-8 bytes), RSA, ECDSA, or X509 |
| `TokenValidationParameters` | Optional override of validation parameters |

With a JWT session, call `modelBuilder.UseRefreshToken()` on your `DbContext` and migrate.

## Email code

`.AddEmailCode(options => …)` takes `EmailCodeOptions`. A composed host calls `AddEmailCodeEndpoints<TUser>(options => …)` with the same options.

`EmailCodeOptions` defaults and validation are in the [Email-code module](/modules/email-code#options). `AllowSignUp` and `MagicLink.Enabled` default to `false`. `ReAuth` defaults to enabled and 5 minutes, and the proof is offered only when the user has no password, authenticator, or passkey. Call `modelBuilder.UseEmailCodes()` and add a migration before deploying.

To finish verify in a JWT, add `.AddJwt(...)` and map `AuthEndpointsSession.Jwt`. On a composed host, call `AddJwtEndpoints` and pass `AuthEndpointsSession.Jwt` to `MapEmailCodeEndpoints`.

## ReAuth

`AuthEndpointsReAuthOptions`:

| Property | Default | Description |
| --- | --- | --- |
| `Lifetime` | 5 minutes | Cookie `ExpireTimeSpan`, ticket `ExpiresUtc`, and header `reauthToken` expiry for the same confirm. Non-persistent (`IsPersistent = false`). No sliding expiration. |

Startup validation rejects `<= 0`, `InfiniteTimeSpan`, values under 1 minute, and values over 60 minutes.

A builder host and a composed host configure the same type:

```cs
builder.Services.Configure<AuthEndpointsReAuthOptions>(o =>
{
    o.Lifetime = TimeSpan.FromMinutes(2);
});
```

## Example

```cs
builder.Services.AddAuthEndpoints<AppUser>(o =>
    {
        o.EmailConfirmation.ConfirmEmailRedirectUri = "/email-confirmed";
    }).AddEntityFrameworkStores<AppDbContext>()
    .ConfigureIdentity(identity => identity.Password.RequiredLength = 10)
    .AddPassword()
    .AddJwt(jwt =>
    {
        jwt.Issuer = "https://example.com";
        jwt.Audience = "https://example.com";
        jwt.SigningOptions.SymmetricKey = builder.Configuration["Jwt:SymmetricKey"];
    });
builder.Services.Configure<AuthEndpointsReAuthOptions>(o =>
{
    o.Lifetime = TimeSpan.FromMinutes(2);
});

app.MapAuthEndpoints<AppUser>("/api/auth", AuthEndpointsSession.Jwt);
```

For stacks that skip the builder, see [Composition rules](/composables#follow-the-composition-rules).
