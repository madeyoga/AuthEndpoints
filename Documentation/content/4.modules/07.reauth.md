ReAuth (step-up) confirms the user's identity before sensitive mutations. It is included when you map [Identity management](/modules/identity-management) (with antiforgery in the management map).

## Schemes and header

| Piece | Value |
| --- | --- |
| Cookie scheme | `AuthEndpoints.ReAuth` (default 5 minutes, `ReAuth.Lifetime`) |
| Bearer scheme | `AuthEndpoints.ReAuth.Bearer` |
| Header | `X-AuthEndpoints-Reauth` with `reauthToken` |
| Policy | `ReAuthPolicy` (no authentication schemes) |

## Routes

Mapped with management. `POST /confirmIdentity` and `POST /confirmIdentity/passkeyOptions` use `AuthEndpoints.ConfirmIdentity`. `POST /confirmIdentity/emailCode/send` is mapped by `MapAccountManagementEndpoints` and `MapReAuthEndpoints` when `AddEmailCodeEndpoints` was called, and it uses `AuthEndpoints.ConfirmIdentity.EmailCode`. The `AddAuthEndpoints` / `MapAuthEndpoints` facade does not map that send route, and its `authMethods.emailCode` stays false. `MapIdentityManagementApi` adds antiforgery to these `POST` routes, so send `RequestVerificationToken` on each:

| Method | Path | Notes |
| --- | --- | --- |
| `GET` | `/manage/authMethods` | Available step-up methods, including `emailCode` |
| `POST` | `/confirmIdentity` | Exactly one proof; CSRF when mapped via management |
| `POST` | `/confirmIdentity/emailCode/send` | No body. Sends a step-up code when email-code endpoints are registered |
| `POST` | `/confirmIdentity/passkeyOptions` | WebAuthn options for passkey step-up; CSRF when mapped via management |

### ConfirmIdentity proof

Provide **exactly one** of:

- `password`
- `twoFactorCode`
- `twoFactorRecoveryCode`
- `credentialJson` (passkey assertion)
- `emailCode` (after `POST /confirmIdentity/emailCode/send`, when `emailCode` is true)

On success the body is `{ "reauthToken" }`. Cookie sign-ins also set `AuthEndpoints.ReAuth`. A caller authenticated with `Authorization: Bearer` (Identity bearer or JWT) gets the token only. Cookie and token share the same lifetime and both include the user's security stamp.

`emailCode` is offered only when `AddEmailCodeEndpoints` is registered, `EmailCode.ReAuth.Enabled` is true (the default), the account email is confirmed, and the user has no password, no authenticator, and no passkey. An external login does not hide the proof. The 3.x facade keeps `emailCode` false and does not map `POST /confirmIdentity/emailCode/send`.

That send route has no body. It requires the signed-in user and a CSRF token when management mapped it. The rate limit is `AuthEndpoints.ConfirmIdentity.EmailCode` (3 requests per minute per user). The `200` body is `{ "expiresInSeconds", "resendAfterSeconds" }`. The code lasts `EmailCode.ReAuth.CodeLifetime` (default 5 minutes, 1 through 10). It is single use. A security-stamp change invalidates it. The message purpose is `ReAuth` (`2`) and `LinkUrl` is null. Cooldown and the per-address send cap are separate from sign-in codes. A wrong code counts toward lockout when `CountFailuresTowardLockout` is true. Five wrong attempts is the default cap.

The step-up credential is an extra proof on top of a sign-in. It is never a sign-in by itself, and it never replaces `HttpContext.User`. `ReAuthPolicy` adds no authentication schemes. The requirement looks at the user the route already authenticated, then authenticates the ReAuth cookie and `X-AuthEndpoints-Reauth`. It succeeds only when that proof has `Reauth=true`, the same user id, and, when the store supports security stamps, the user's current security stamp. A missing stamp claim is rejected. A password change, reset, or `UpdateSecurityStampAsync` cancels outstanding cookies and tokens. A request with only the cookie or the header is rejected (`401` or `403`). A signed-in user with no proof, an expired proof, a proof issued to someone else, or a stale stamp gets `403`.

Pair `.RequireReauth()` with `.RequireAuthorization()` that signs the user in. Account management, passkey mutations, and external unlink use the registered application-cookie, Identity bearer, and JWT bearer schemes. `.RequireReauth()` alone does not authenticate those schemes. A route that omits the sign-in authorization fails.

## Lifetime

Default is **5 minutes**, non-persistent, no sliding expiration. Set `AuthEndpointsOptions.ReAuth.Lifetime` (a `TimeSpan`) on the facade, or `IOptions<AuthEndpointsReAuthOptions>` on a composable host. One value drives confirm `ExpiresUtc`, cookie `ExpireTimeSpan`, and `reauthToken` expiry.

Valid range: 1 minute through 60 minutes. Startup rejects zero, negative, over 60 minutes, and `InfiniteTimeSpan`.

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(o =>
{
    o.ReAuth.Lifetime = TimeSpan.FromMinutes(2);
});
```

## Protecting host endpoints

```cs
builder.Services.AddCookieAuthEndpoints(); // or AddBearerAuthEndpoints. Both register the ReAuth schemes.

app.MapPost("/billing/update", handler)
    .RequireAuthorization() // list the sign-in schemes this route accepts
    .RequireReauth();
```

`.RequireAuthorization()` without schemes uses the host default sign-in. Pass the Identity bearer and JWT schemes when those tokens should count, the same way management routes do. A signed-in caller without a matching proof gets `403`.

## Typical client flow

The password facade uses the prefix `/auth`. The 3.x facade uses `/identity`.

1. `GET /identity/manage/authMethods`
2. Collect proof (password, 2FA, passkey via `POST /identity/confirmIdentity/passkeyOptions`, or `emailCode` via `POST /identity/confirmIdentity/emailCode/send`)
3. `POST /identity/confirmIdentity` with CSRF
4. Retry the sensitive action with ReAuth cookie and/or `X-AuthEndpoints-Reauth`

## Where ReAuth is required

- Manage 2FA, info, and set-password mutations
- Passkey add, rename, delete, and creation options
- External OAuth unlink
- Any host endpoint with `.RequireReauth()`
