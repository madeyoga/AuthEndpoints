5.0 is in development on the `release/5.0` branch. This page lists the breaking changes merged there so far, and the migration for each.

The routes, the database schema, the cookies, and the token formats do not change unless a section says so. An upgrade adds the `AuthEndpoints.EntityFrameworkCore` package and changes `Program.cs`. It does not need a migration and does not sign anyone out.

## AddAuthEndpoints is a builder

`AddAuthEndpoints<TUser>()` returns `AuthEndpointsBuilder`. `.AddEntityFrameworkStores<TContext>()` adds the EF Core stores (see [EF Core storage is a separate package](#ef-core-storage-is-a-separate-package)). Each other builder method turns on one sign-in method or session, and `MapAuthEndpoints<TUser>(path, session)` maps exactly what was added under one prefix. See [AddAuthEndpoints](/modules/add-auth-endpoints).

```cs
builder.Services.AddAuthEndpoints<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddPassword()
    .AddPasskeys(passkeys => passkeys.ServerDomain = "example.com")
    .AddEmailCode();

app.UseAuthEndpoints();
app.MapAuthEndpoints<AppUser>("/auth", AuthEndpointsSession.Cookie);
```

Migration. Replace the 4.x entry point you use with the builder, as in the next two sections.

## The 3.x facade is removed

The 3.x facade is gone: the `AddAuthEndpoints` overloads that took `AuthEndpointsOptions` with `IdentityPath`, `SignIn`, `PasskeyPath`, `Passkeys`, `Jwt`, and `EmailCode`, the `AddAuthEndpoints(AuthEndpointsSignIn, …)` overloads, `AuthEndpointsSignIn`, and the parameterless `MapAuthEndpoints<TUser>()`. Code that calls them no longer compiles.

| 4.x | 5.0 |
| --- | --- |
| `AddAuthEndpoints<TUser, TContext>(o => …)` | `AddAuthEndpoints<TUser>().AddEntityFrameworkStores<TContext>().AddPassword()` |
| `AuthEndpointsSignIn.Cookie` | `MapAuthEndpoints(path, AuthEndpointsSession.Cookie)` |
| `AuthEndpointsSignIn.IdentityBearer` | `.AddIdentityBearer()` and `AuthEndpointsSession.IdentityBearer` |
| `o.Passkeys.Enabled` (default `true`), `o.Passkeys.ServerDomain` | `.AddPasskeys(p => p.ServerDomain = …)`. Passkeys are off unless you call it. |
| `o.Jwt.Enabled`, `o.Jwt.Configure` | `.AddJwt(jwt => …)` |
| `o.EmailCode.Enabled`, `o.EmailCode.Configure` | `.AddEmailCode(options => …)` |
| `o.RequireConfirmedAccount`, `o.ConfigureIdentity` | `.ConfigureIdentity(identity => …)`. `RequireConfirmedAccount` still defaults to `true`. |
| `o.ConfigurePasskeys` | `Configure<IdentityPasskeyOptions>` |
| `o.ReAuth.Lifetime` | `Configure<AuthEndpointsReAuthOptions>(o => o.Lifetime = …)` |
| `o.EmailConfirmation`, `o.RequireEmailSenderInProduction` | Unchanged, on the `AddAuthEndpoints` callback |

The facade mapped three prefixes: `/identity` for management and sign-in, `/account` for passkeys, and `/auth` for JWT. `MapAuthEndpoints` maps one prefix for one session. To keep the 4.x routes, compose the building blocks on those prefixes:

```cs
var identity = app.MapGroup("/identity");
identity.MapIdentityManagementApi<AppUser>();
identity.MapCookieAuthEndpoints<AppUser>();
app.MapGroup("/account").MapPasskeyEndpoints<AppUser>();
```

Register `AddCookieAuthEndpoints()` and `AddPasskeyEndpoints<AppUser>()` for that map. Those maps are in the `AuthEndpoints.Identity` and `AuthEndpoints.Passkey` namespaces. The Identity bearer facade used `MapBearerAuthEndpoints` and `AddBearerAuthEndpoints` instead, and passed `AuthEndpointsSession.IdentityBearer` to `MapPasskeyEndpoints`.

The facade kept the 3.4.1 handlers for password login, JWT `POST /create`, and email-code verify. `MapAuthEndpoints` uses the current handlers, so failure bodies, lockout counting, and the unknown-email hash verify follow [Password login](/concepts/security-model#password-login). It also maps `POST` and `DELETE /manage/password` and `POST /confirmIdentity/emailCode/send`, which the facade left out, and `authMethods.emailCode` can be `true`.

On a cookie session, passkey register and login sign in with the application cookie whether or not the client sends `?useCookies=true`. The cookie facade returned an Identity bearer token when the flag was missing. Identity bearer sessions still honour the flag.

Migration. Move each option to the builder call in the table. If clients call the `/identity` or `/account` routes, either point them at the new prefix or compose the building blocks as shown.

## The password preset is removed

`AddPasswordAuth`, `MapPasswordAuth`, `PasswordAuthOptions`, and `PasskeyScenarioOptions` are removed. The builder covers the same host:

| 4.x | 5.0 |
| --- | --- |
| `AddPasswordAuth<TUser, TContext>()` | `AddAuthEndpoints<TUser>().AddEntityFrameworkStores<TContext>().AddPassword()` |
| `MapPasswordAuth<TUser>()` | `MapAuthEndpoints<TUser>("/auth", AuthEndpointsSession.Cookie)` |
| `o.Path` | The `path` argument of `MapAuthEndpoints` |
| `o.Session = AuthEndpointsSession.Jwt`, `o.Jwt = jwt => …` | `.AddJwt(jwt => …)` and `AuthEndpointsSession.Jwt` |
| `o.Passkeys.ServerDomain` | `.AddPasskeys(p => p.ServerDomain = …)` |
| `o.RequireConfirmedAccount`, `o.ConfigureIdentity` | `.ConfigureIdentity(identity => …)` |
| `o.EmailConfirmation`, `o.RequireEmailSenderInProduction` | The `AddAuthEndpoints` callback, or `Configure<AuthEndpointsOptions>` |

The routes under the prefix are the same. A later `Configure<AuthEndpointsOptions>` now applies to `EmailConfirmation`. There is no copy step, and nothing is fixed at registration except what the builder methods add.

Migration. Replace the two calls as in the table.

## AuthEndpointsOptions holds only runtime settings

`AuthEndpointsOptions` keeps `EmailConfirmation` and `RequireEmailSenderInProduction`. `EmailConfirmation` is now `EmailConfirmationOptions`. `AuthEndpointsEmailConfirmationOptions`, `AuthEndpointsPasskeyOptions`, `AuthEndpointsJwtOptions`, and `AuthEndpointsEmailCodeOptions` are removed. A composed host that sets the confirm-email redirect with `Configure<AuthEndpointsOptions>` keeps working.

Migration. Replace `AuthEndpointsEmailConfirmationOptions` with `EmailConfirmationOptions` where you name the type.

## IAccountSecurityEmailSender is replaced by IAccountSecurityNotifier

`IAccountSecurityEmailSender<TUser>` and `LoggingAccountSecurityEmailSender<TUser>` are removed. In their place, `IAccountSecurityNotifier<TUser>` has one method, `NotifyAsync(AccountSecurityEvent<TUser>)`. The event carries `Kind`, `User`, and `Email`. A kind added in a later version reaches your notifier without a new method, so it is not lost behind a default no-op, as `SendPasswordRemovedAsync` was in 4.x.

| 4.x | 5.0 `AccountSecurityEventKind` |
| --- | --- |
| `SendPasswordSetAsync(user, email)` | `PasswordSet` |
| `SendPasswordRemovedAsync(user, email)` | `PasswordRemoved` |
| `SendRegistrationAttemptedAsync(user, email)` | `RegistrationAttempted` |
| `LoggingAccountSecurityEmailSender<TUser>` | `LoggingAccountSecurityNotifier<TUser>`, still the default |

One behavior changes. 4.x skipped the password-set and password-removed notices for an account with no email. 5.0 raises the event with `Email` null, so a notifier can reach that account another way, or ignore it.

```cs
public sealed class QueuedSecurityNotifier(
    System.Threading.Channels.Channel<AccountSecurityEvent<AppUser>> queue) : IAccountSecurityNotifier<AppUser>
{
    public async Task NotifyAsync(AccountSecurityEvent<AppUser> securityEvent, CancellationToken cancellationToken = default)
    {
        // No address (an account that signs in by user name): nobody to email.
        if (securityEvent.Email is null)
        {
            return;
        }

        // Queue it. A background service sends one message per Kind, and skips kinds it does not know.
        await queue.Writer.WriteAsync(securityEvent, cancellationToken);
    }
}
```

Migration. Implement `IAccountSecurityNotifier<TUser>`, switch on `Kind`, and register it in place of the sender, for example `builder.Services.AddSingleton<IAccountSecurityNotifier<AppUser>, QueuedSecurityNotifier>()`. Handle a null `Email` and kinds you do not know.

## JwtSessionOptions is merged into SimpleJwtOptions

4.x had two options classes for the JWT feature. `SimpleJwtOptions.RefreshTokenTransport` was copied onto `JwtSessionOptions` only when it was not `Cookie`, so which value won depended on the value and on the order of the calls. 5.0 has one class. `JwtSessionOptions` and `JwtSessionOptionsValidator` are removed, and `SimpleJwtOptions` gains their lifetimes:

| 4.x | 5.0 |
| --- | --- |
| `JwtSessionOptions.RefreshTokenTransport` | `SimpleJwtOptions.RefreshTokenTransport` |
| `JwtSessionOptions.RefreshTokenLifetime` | `SimpleJwtOptions.RefreshTokenLifetime` |
| `JwtSessionOptions.AbsoluteLifetime` | `SimpleJwtOptions.AbsoluteLifetime` |
| `JwtSessionOptionsValidator` | `SimpleJwtOptionsValidator` checks the lifetimes too |
| `RefreshTokenService<TContext>(db, time, IOptions<JwtSessionOptions>)` | `RefreshTokenService(store, time, IOptions<SimpleJwtOptions>)`. See [Storage goes through store interfaces](#storage-goes-through-store-interfaces) |

Set every JWT setting in the `AddJwt` or `AddJwtEndpoints` callback. The options are fixed when that call runs, because the signing key also configures JWT bearer validation. `Configure<SimpleJwtOptions>` afterwards has no effect. The defaults are unchanged: `Cookie`, 14 days, and 14 days.

Migration. Move a `Configure<JwtSessionOptions>(session => …)` into the JWT callback:

```cs
builder.Services.AddAuthEndpoints<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>()
    .AddPassword()
    .AddJwt(jwt =>
    {
        jwt.SigningOptions.SymmetricKey = key;
        jwt.RefreshTokenTransport = RefreshTokenTransport.Body;
        jwt.AbsoluteLifetime = TimeSpan.FromDays(30);
    });
```

## The endpoint handlers are internal

The handler classes are internal: `IdentityApiEndpoints<TUser>`, `JwtEndpoints<TUser>`, `PasskeyEndpoints<TUser>`, `EmailCodeEndpoints<TUser>`, `ReAuthEndpoints<TUser>`, `ExternalAuthEndpoints<TUser>`, and `ExternalAccountEndpoints<TUser>`. The public surface is the `Add*` and `Map*` methods and the HTTP contract they map. A handler can change without a breaking release, as long as its route keeps the same request, response, and status codes.

The request and response bodies that came from `Microsoft.AspNetCore.Identity.Data` are now library types in `AuthEndpoints.Identity`:

| 4.x | 5.0 |
| --- | --- |
| `LoginRequest` | `PasswordLoginRequest` |
| `RegisterRequest` | `PasswordRegisterRequest` |
| `RefreshRequest` | `BearerRefreshRequest` |
| `ResendConfirmationEmailRequest` | `ConfirmationEmailRequest` |
| `ForgotPasswordRequest` | `PasswordRecoveryRequest` |
| `ResetPasswordRequest` | `PasswordResetRequest` |
| `InfoRequest`, `InfoResponse` | `AccountInfoRequest`, `AccountInfoResponse` |
| `TwoFactorRequest`, `TwoFactorResponse` | `TwoFactorSettingsRequest`, `TwoFactorSettingsResponse` |
| An untyped body on `GET /manage/2fa` | `TwoFactorStatusResponse` |

The JSON is the same: the same property names, the same order, and the same required members. `AccountInfoResponse.Email` is `string?`, so an account without an email gets `"email": null`, as 4.x already sent.

The OpenAPI schema names follow the new type names. A client generated from the OpenAPI document gets new type names after you regenerate it. The JSON it sends and reads does not change.

`AuthEndpoints.External.OAuth` no longer forwards `ExternalAuthEndpoints<TUser>` or `ExternalAccountEndpoints<TUser>`, because they are internal. Its other forwards are unchanged.

Migration. If you mapped a handler yourself, for example `app.MapPost("/login", IdentityApiEndpoints<AppUser>.Login)`, map the matching building block instead, such as `MapPasswordSignInEndpoints`. See [Composition](/modules/composition). If your .NET client deserialized `Microsoft.AspNetCore.Identity.Data.InfoResponse`, it keeps working, or you can switch it to `AccountInfoResponse`, which allows a null email.

## The per-method sign-in completers are removed

4.0 marked these obsolete, with "Removed in 5.0". They are gone:

| Removed | Use |
| --- | --- |
| `IEmailCodeSignInCompleter<TUser>`, `EmailCodeSignInContext`, `AddEmailCodeSignInCompleter` | `ISignInCompleter<TUser>`, `SignInCompletionContext`, `AddSignInCompleter<TUser, TCompleter>(name)` |
| `IPasskeySignInCompleter<TUser>`, `PasskeySignInCompletionContext`, `AddPasskeySignInCompleter` | The same |
| `IExternalLoginCompleter<TUser>`, `ExternalAuthBuilder.AddCompleter<T>()` | The same, with `SignInMethod.External` |
| `IdentityEmailCodeSignInCompleter`, `IdentityPasskeySignInCompleter`, `CookieExternalLoginCompleter` | The built-in `IdentityBearer` and `Cookie` completers |
| `JwtEmailCodeSignInCompleter`, `JwtPasskeySignInCompleter`, `JwtExternalLoginCompleter` | The built-in `Jwt` completer (`AuthEndpointsSession.Jwt`) |
| `AnyCallerAuthenticationBuilderExtensions.SchemeName` | `AuthEndpointsConstants.AnyCallerScheme` |

`PasskeySignInKind` stays. It is now in its own file and is used by `SignInCompletionContext.PasskeyKind`.

A sign-in now has one path. It uses the session or completer name the map passed, else `SignInCompletionOptions.Default` on a map that honors it, else a built-in default: the completer registered as `IdentityBearer` for email code and passkeys, and the one registered as `Cookie` for external sign-in. Those defaults behave as the removed `Identity*` and `CookieExternalLoginCompleter` types did. One consequence: replacing the `IdentityBearer` or `Cookie` name with `AddSignInCompleter` now also replaces that default. In 4.x a separate obsolete completer still ran there.

`AuthEndpoints.External.OAuth` no longer forwards the three external completer types. `AuthEndpoints.OpenIddict` wraps only `ISignInCompleter<TUser>` to add `amr`, because that is now the only completer type.

Migration. Move each custom completer to `ISignInCompleter<TUser>`, register it with `AddSignInCompleter<TUser, TCompleter>("MyName")`, and pass `"MyName"` to the map or set it as `SignInCompletionOptions.Default`. Replace `SchemeName` with `AuthEndpointsConstants.AnyCallerScheme`.

## EF Core storage is a separate package

The `AuthEndpoints` package no longer depends on EF Core. The EF Core stores, entity mappings and `ModelBuilder` extensions moved to `AuthEndpoints.EntityFrameworkCore`, which ships with `AuthEndpoints` under the same version. Their namespaces did not change, so your `using` lines keep working.

```bash
dotnet add package AuthEndpoints.EntityFrameworkCore
```

Setup no longer takes a `DbContext` type. Pass it once, to the stores:

| 4.x and earlier 5.0 previews | 5.0 |
| --- | --- |
| `AddAuthEndpoints<TUser, TContext>()` | `AddAuthEndpoints<TUser>().AddEntityFrameworkStores<TContext>()` |
| `AddAuthEndpoints<TUser, TRole, TContext>()` | `AddAuthEndpoints<TUser>().AddRoles<TRole>().AddEntityFrameworkStores<TContext>()`. Call `AddRoles` first: after the stores it throws |
| `AuthEndpointsBuilder<TUser, TContext>` | `AuthEndpointsBuilder` |
| `AddAuthEndpointsIdentity<TUser, TContext>()` | `AddAuthEndpointsIdentity<TUser>().AddEntityFrameworkStores<TContext>()` (Identity's own extension) |
| `AddEmailCodeEndpoints<TUser, TContext>()`, `AddEmailCodeSendEndpoints`, `AddEmailCodeSignInEndpoints` | `AddEmailCodeEndpoints<TUser>()` and the others with `<TUser>`, plus `AddAuthEndpointsEntityFrameworkStores<TUser, TContext>()` once |
| `AddJwtEndpoints<TUser, TContext>(…)` | `AddJwtEndpoints<TUser>(…)`, plus `AddAuthEndpointsEntityFrameworkStores<TUser, TContext>()` once |
| `AddActiveSessions<TUser, TContext>(…)` | `AddActiveSessions<TUser>(…)`, plus `AddAuthEndpointsEntityFrameworkStores<TUser, TContext>()` once |
| `EntityFrameworkCoreHelpers.UseRefreshToken` | `RefreshTokenModelBuilderExtensions.UseRefreshToken`. Calls written as `modelBuilder.UseRefreshToken()` do not change |

A 4.x call with two type arguments no longer compiles, so the compiler lists every place to change. Without stores, mapping fails with a message that names the missing interface, for example `IUserStore<AppUser>` or `IEmailCodeStore`. In Development, `Build()` checks services first and names it in its own error.

`UseEmailCodes()`, `UseRefreshToken()` and `UseActiveSessions()` keep their names and tables. A feature whose table is not mapped now fails when its endpoints are mapped, naming the call to add; JWT used to fail at the first refresh.

### Storage goes through store interfaces

In 4.x the email-code, refresh-token and active-session rules lived inside EF Core classes. 5.0 keeps the rules in AuthEndpoints and reads and writes rows through three public interfaces. `AddEntityFrameworkStores` registers the EF Core implementations; to use other storage, register your own:

| Interface | Used by | Rows |
| --- | --- | --- |
| `IEmailCodeStore` | `AddEmailCode`, `AddEmailCodeEndpoints` | `EmailCodeEntry` |
| `IRefreshTokenStore` | `AddJwt`, `AddJwtEndpoints` | `RefreshToken` |
| `IActiveSessionStore` | `AddActiveSessions` | `ActiveSession` |

Each method is one atomic operation, and its XML docs say what must hold under concurrency. A store never sees a raw code, link token or refresh token. Email addresses arrive hashed, except `EmailCodeEntry.SignupEmail`, which a sign-up row keeps in plain text so that the magic link can create the account.

What else changes:

| 4.x | 5.0 |
| --- | --- |
| `RefreshTokenService<TContext>` | `RefreshTokenService`, over `IRefreshTokenStore`. Resolve `IRefreshTokenService` from DI instead of constructing it |
| `IRefreshTokenService` methods had no cancellation token | Each takes an optional `CancellationToken`. AuthEndpoints passes the request's token to lookups, creates and rotations, but not to the revokes that reuse detection and logout depend on |
| The session store kept a hidden `SessionId` column on refresh tokens | `RefreshToken.SessionId`. EF Core still maps it only when you call `UseActiveSessions()`, so the schema is unchanged |
| Email-code sign-up caught `DbUpdateException` when two requests created the same account | `IUserCreateFailureHandler<TUser>` decides which exceptions mean a refused insert. `AddEntityFrameworkStores` registers the EF Core one |

The database schema is unchanged, so no migration is needed.

Migration. Add the package and move the `DbContext` type from the setup calls to `AddEntityFrameworkStores`, as in the first table. Code that constructed `RefreshTokenService<TContext>` should resolve `IRefreshTokenService`, or construct `RefreshTokenService` with an `IRefreshTokenStore`. A custom `IRefreshTokenService` adds the `CancellationToken` parameters.
