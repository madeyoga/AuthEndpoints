`AddAuthEndpoints` and `MapAuthEndpoints` are the 3.x facade, kept for compatibility. They are not obsolete. Names, options, `AuthEndpointsSignIn`, `EmailCode.Enabled`, and the `/identity`, `/account`, and `/auth` routes stay at 3.4.1. New hosts that want one password session use [Password auth](/getting-started/password-auth). Do not call both facades in one host.

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(options =>
{
    options.Passkeys.ServerDomain = "example.com";
});

app.UseAuthEndpoints();
app.MapAuthEndpoints<AppUser>();
```

Identity bearer is `AddAuthEndpoints<AppUser, AppDbContext>(AuthEndpointsSignIn.IdentityBearer, ...)`. JWT on this facade is `options.Jwt.Enabled = true` plus `Jwt.Configure`. The [quick start](/getting-started/quick-start) walks through cookie sign-in on these routes.

The facade does not gain 4.0-only behaviour, with three exceptions:

- A `RefreshTokenTransport` other than `Cookie` in `Jwt.Configure` is applied. `AddJwtEndpoints` copies that non-default value onto `JwtSessionOptions`. The default `Cookie` leaves an earlier `Configure<JwtSessionOptions>` in place.
- `POST /auth/create` runs a password-hash verify when the email is unknown, because that handler calls `DefaultAuthenticator`. Facade login does not.
- JWT refresh uses the 4.0 rotation rules: reuse revokes the family, the family has an absolute lifetime, the token is bound to the security stamp, and logout revokes it on the server. See [Upgrade to 4.0](/guides/upgrading-to-4).

`POST /manage/password`, email-code step-up, and `completer` selection are not on this facade. Password login, JWT `POST /create` failure text, and email-code verify stay on the 3.4.1 handlers. Option renames do not ship. The shared JWT `POST /create` responses and the password `/login` pipeline do not apply here, apart from the unknown-email hash verify on `POST /create`.

There is no role overload on `AddPasswordAuth`. The three-type `AddAuthEndpoints<TUser, TRole, TContext>` overload is unchanged.
