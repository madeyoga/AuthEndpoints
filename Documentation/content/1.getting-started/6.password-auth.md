`AddPasswordAuth` and `MapPasswordAuth` are the password facade. One call registers Identity, password sign-up, sign-in, and recovery, account management, and one session. Cookie is the default. JWT is the other choice. Passkeys are included when you set a relying-party domain.

The facade is a fixed list of building-block calls. It adds no routes of its own. The expansion is on this page, so moving off the facade is copy and paste.

`AddAuthEndpoints` / `MapAuthEndpoints` stay the 3.4.1 compatibility facade (`/identity`, `/account`, `/auth`). Do not call both facades in one host. Identity bearer stays on `AddAuthEndpoints`. There is no role overload on `AddPasswordAuth`.

You need the .NET 10 SDK.

## Cookie session

```cs
using AuthEndpoints;
using Microsoft.AspNetCore.Identity;
using Microsoft.AspNetCore.Identity.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlite("Data Source=app.db"));

builder.Services.AddPasswordAuth<AppUser, AppDbContext>(o =>
{
    o.Passkeys.ServerDomain = "localhost";
});

builder.Services.AddTransient<IEmailSender<AppUser>, ConsoleEmailSender>();

var app = builder.Build();

using (var scope = app.Services.CreateScope())
{
    scope.ServiceProvider.GetRequiredService<AppDbContext>().Database.EnsureCreated();
}

app.UseAuthEndpoints();
app.MapPasswordAuth<AppUser>();

app.Run();

public class AppUser : IdentityUser { }

public class AppDbContext(DbContextOptions<AppDbContext> options) : IdentityDbContext<AppUser>(options) { }

public class ConsoleEmailSender(ILogger<ConsoleEmailSender> logger) : IEmailSender<AppUser>
{
    public Task SendConfirmationLinkAsync(AppUser user, string email, string confirmationLink)
    {
        logger.LogInformation("Confirm {Email}: {Link}", email, confirmationLink);
        return Task.CompletedTask;
    }

    public Task SendPasswordResetLinkAsync(AppUser user, string email, string resetLink)
    {
        logger.LogInformation("Reset link for {Email}: {Link}", email, resetLink);
        return Task.CompletedTask;
    }

    public Task SendPasswordResetCodeAsync(AppUser user, string email, string resetCode)
    {
        logger.LogInformation("Reset code for {Email}: {Code}", email, resetCode);
        return Task.CompletedTask;
    }
}
```

Every route is under `/auth`. Register, confirm the link from the log (`&amp;` in the log is `&`), then sign in:

```bash
curl -i -c cookies.txt -b cookies.txt -H "Content-Type: application/json" \
  -d '{"email":"ada@example.com","password":"Passw0rd!"}' \
  http://localhost:5265/auth/login
```

The response is `200 OK` with `Set-Cookie: .AspNetCore.Identity.Application`. `GET /auth/manage/info` with that cookie returns the account. Cookie-mode account routes (`/manage` and `/confirmIdentity`) also accept `Identity.Bearer`. The facade does not map Identity bearer login; Identity registers that scheme, and those routes include it. Sign-out is `POST /auth/logout` with a CSRF token from `GET /auth/csrfToken` in the `RequestVerificationToken` header.

`RequireConfirmedAccount` is true, so login before confirm is `401`.

## JWT session

Set `Session` to `AuthEndpointsSession.Jwt` and pass a `Jwt` callback. The callback is required. A missing signing key fails while the host is being built.

JWT stores refresh tokens, so the `DbContext` calls `UseRefreshToken()` and you add a migration before production. `EnsureCreated` is only for this local sample.

```cs
builder.Services.AddPasswordAuth<AppUser, AppDbContext>(o =>
{
    o.Session = AuthEndpointsSession.Jwt;
    o.Passkeys.ServerDomain = "example.com";
    o.Jwt = jwt =>
    {
        jwt.Issuer = "https://example.com";
        jwt.Audience = "https://example.com";
        jwt.SigningOptions.SymmetricKey = key;
        jwt.RefreshTokenTransport = RefreshTokenTransport.Cookie;
    };
});
```

Password sign-in is `POST /auth/create`, not `POST /auth/login`. The response is `{ "accessToken", "tokenType": "Bearer" }`. Cookie transport sets `AuthEndpoints.Jwt.RefreshToken` and omits `refreshToken`. `GET /auth/verify` with `Authorization: Bearer` returns `204`. `POST /auth/refresh` and `POST /auth/logout` take the CSRF token from `GET /auth/csrfToken`. Logout revokes the refresh family.

For a native or CLI client, set `jwt.RefreshTokenTransport = RefreshTokenTransport.Body`. Sign-in and refresh then also include `refreshToken`. `POST /auth/refresh` and `POST /auth/logout` take `{ "refreshToken" }`, skip antiforgery, and `GET /auth/csrfToken` is not mapped.

`AddJwtEndpoints` copies `SimpleJwtOptions.RefreshTokenTransport` onto `JwtSessionOptions` only when that value is not `Cookie`. `AddPasswordAuth` and the 3.4.1 facade pass their JWT callback through `AddJwtEndpoints`, so a `Body` value is applied there. The default `Cookie` matches 3.4.1 and leaves an earlier `Configure<JwtSessionOptions>` in place. A `Configure<JwtSessionOptions>` registered after `AddJwtEndpoints` replaces it.

## Options

| Property | Default | Description |
| --- | --- | --- |
| `Session` | `Cookie` | `Cookie` or `Jwt`. `IdentityBearer` fails startup validation. |
| `Path` | `/auth` | Rooted prefix for every route this facade maps. |
| `RequireConfirmedAccount` | `true` | Applied before `ConfigureIdentity`, which can replace it. |
| `Passkeys.ServerDomain` | `null` | When set, passkey sign-in and management are mapped. Omit it to leave passkeys off. |
| `EmailConfirmation` | unset | SPA redirect after `GET` confirm-email. Copied onto `AuthEndpointsOptions`, which the handler reads. |
| `Jwt` | `null` | Required when `Session` is `Jwt`. Signing key, issuer, audience, and optional refresh transport. |
| `ConfigureIdentity` | `null` | Optional `Action<IdentityOptions>` after `RequireConfirmedAccount`. |
| `RequireEmailSenderInProduction` | `true` | Production must register a real `IEmailSender<TUser>`. |

In Production, a whitespace `Passkeys.ServerDomain` fails validation. Leaving it null does not. An absolute confirm-email redirect needs `AllowedRedirectOrigins` and `https`. Calling `AddPasswordAuth` and `AddAuthEndpoints` in the same host fails validation, in either order. Calling `AddPasswordAuth` twice throws.

`Session`, `Path`, and `Passkeys.ServerDomain` are fixed by the `AddPasswordAuth` callback. `MapPasswordAuth` maps that snapshot. A later `Configure<PasswordAuthOptions>` that changes any of them fails validation. `EmailConfirmation` can still be configured later. It is copied onto `AuthEndpointsOptions` when those options are resolved.

## Routes

Cookie session, prefix `/auth`:

| Method | Path | Notes |
| --- | --- | --- |
| `POST` | `/auth/register` | Sends a confirmation link |
| `POST` | `/auth/login` | Application cookie. `401` until the email is confirmed |
| `POST` | `/auth/forgotPassword` | |
| `POST` | `/auth/resetPassword` | |
| `POST` | `/auth/logout` | CSRF |
| `GET` | `/auth/csrfToken` | |
| `GET` | `/auth/confirmEmail` | |
| `POST` | `/auth/resendConfirmationEmail` | Signed in, CSRF |
| `GET` / `POST` | `/auth/manage/info` | Cookie mode accepts `Identity.Application` and `Identity.Bearer` |
| `GET` / `POST` | `/auth/manage/2fa` | |
| `GET` | `/auth/manage/authMethods` | |
| `POST` | `/auth/manage/password` | Sets a password when the account has none |
| `POST` | `/auth/confirmIdentity` | Step-up |

JWT session uses the same management, recovery, and confirm-email routes. It maps `POST /auth/create`, `POST /auth/refresh`, `GET /auth/verify`, and `POST /auth/logout` instead of `POST /auth/login`. Cookie refresh also maps `GET /auth/csrfToken`. `POST /auth/create` returns `accessToken` and `tokenType` (`Bearer`). Body transport adds `refreshToken`. JWT account routes also accept the `Bearer` scheme.

When `Passkeys.ServerDomain` is set, the same prefix also maps passkey sign-in (`requestOptions`, `register/options`, `register`, `login`) and passkey management, plus `POST /auth/confirmIdentity/passkeyOptions`.

Not mapped: email-code sign-in, external sign-in. Hosts that need those compose the building blocks.

## Same routes without the facade

`AddPasswordAuth` / `MapPasswordAuth` expand to these calls. `TUser` and `TContext` are your user and `DbContext` types.

```cs
services.AddAuthEndpointsIdentity<TUser, TContext>(identity =>
{
    identity.SignIn.RequireConfirmedAccount = options.RequireConfirmedAccount;
    options.ConfigureIdentity?.Invoke(identity);
});
services.AddPasswordSignUpEndpoints();
services.AddPasswordSignInEndpoints();
services.AddPasswordRecoveryEndpoints();
services.AddAccountManagementEndpoints();

// Cookie session:
services.AddCookieSessionEndpoints();

// JWT session (options.Jwt is required).
// AddJwtEndpoints copies a non-default SimpleJwtOptions.RefreshTokenTransport.
services.AddJwtEndpoints<TUser, TContext>(options.Jwt);

// When Passkeys.ServerDomain is set:
services.AddPasskeyEndpoints<TUser>();
services.Configure<IdentityPasskeyOptions>(passkeys => passkeys.ServerDomain = options.Passkeys.ServerDomain);

// Confirm-email redirect, read by the shared handler:
services.Configure<AuthEndpointsOptions>(auth =>
{
    auth.EmailConfirmation.ConfirmEmailRedirectUri = options.EmailConfirmation.ConfirmEmailRedirectUri;
    auth.EmailConfirmation.AllowedRedirectOrigins = options.EmailConfirmation.AllowedRedirectOrigins;
});
```

Map under one group. Cookie session:

```cs
var group = app.MapGroup("/auth");
group.MapPasswordSignUpEndpoints<TUser>();
group.MapPasswordSignInEndpoints<TUser>(AuthEndpointsSession.Cookie);
group.MapPasswordRecoveryEndpoints<TUser>();
group.MapCookieSessionEndpoints<TUser>();
group.MapAccountManagementEndpoints<TUser>();
```

JWT session replaces the sign-in and session lines:

```cs
group.MapJwtPasswordEndpoints<TUser>();
group.MapJwtSessionEndpoints<TUser>();
```

When passkeys are on, the same group also calls:

```cs
group.MapPasskeySignInEndpoints<TUser>(session);
group.MapPasskeyManagementEndpoints<TUser>();
```

`session` is `AuthEndpointsSession.Cookie` or `AuthEndpointsSession.Jwt`. Do not also call `MapPasskeyRegisterOptionsEndpoints`. `MapPasskeySignInEndpoints` already maps `register/options` and `register`.
