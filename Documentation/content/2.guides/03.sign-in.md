Pick the sign-in method from the table, then follow its section. Password, passkey, and account examples use the password facade prefix `/auth`. Identity bearer and email-code examples use `/identity`, because the password facade does not map those routes. External sign-in is under `/auth/external`. To pick a call, see [Choose your sign-in setup](/getting-started/choose-a-sign-in-stack).

## Compare the sign-in methods

| Method | Endpoints | Result | CSRF | Two-factor |
| --- | --- | --- | --- | --- |
| [Password, cookie](#sign-in-with-a-password-and-a-cookie) (password facade default) | `POST /auth/login` | Application cookie, empty `200` body | No | `401` with title `RequiresTwoFactor`, or send the code in the first request |
| [Password, Identity bearer](#sign-in-with-a-password-and-identity-bearer-tokens) | `POST /identity/login`, `POST /identity/refresh` | `AccessTokenResponse` JSON | No | `401` with title `RequiresTwoFactor` |
| [Password, JWT](#sign-in-with-a-password-and-a-jwt) | `POST /auth/create`, `POST /auth/refresh` | `{ accessToken, tokenType }` and an HttpOnly refresh cookie | `create`: no. `refresh`: yes. | `401` with the extension `requiresTwoFactor: true` |
| [Passkey](#sign-in-with-a-passkey) | `POST /auth/passkeys/requestOptions`, `POST /auth/passkeys/login` | The facade session. A cookie session sets the application cookie. | Yes | Skipped |
| [GitHub or Google](#sign-in-with-github-or-google) | `GET /auth/external/login/{provider}`, then the callback | Persistent application cookie, or a JWT refresh cookie | No | Skipped |
| [Emailed code](#sign-in-with-an-emailed-code) | `POST /identity/emailCode/send`, `POST /identity/emailCode/verify` | Identity bearer token JSON, an application cookie, or a JWT | No | `401` with title `RequiresTwoFactor` when the user has 2FA on |

Every login request uses the `AuthEndpoints.Login` rate limit. JWT `POST /auth/refresh` uses it too. Identity bearer `POST /identity/refresh` has no rate limit. See [Rate-limit policies](/modules/rate-limits).

## Sign in with a password and a cookie

`MapPasswordAuth` maps `POST /auth/login`. The body is Identity's `LoginRequest`: `{ "email", "password", "twoFactorCode"?, "twoFactorRecoveryCode"? }`. Registration sets the user name to the email, so the email matches. The password check and the session write are in [Password login](/concepts/security-model#password-login).

1. Send the credentials with `credentials: 'include'`. Login does not need a CSRF token.

   ```js
   const response = await fetch('/auth/login', {
     method: 'POST',
     credentials: 'include',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({ email, password })
   });
   ```

2. The cookie is a session cookie. Add `?useSessionCookies=false` to keep it after the browser closes. This route ignores `useCookies`. The same flag table is in [Cookie sign-in](/modules/cookie-auth#login-query-string).
3. Check the response:
   - `200` with an empty body and a `Set-Cookie` header for `.AspNetCore.Identity.Application`: the user is signed in.
   - `401` with title `RequiresTwoFactor`: ask for a code. See [Enter a two-factor code or a recovery code](#enter-a-two-factor-code-or-a-recovery-code).
   - `401` with title `Unauthorized` and detail `Invalid credentials.`: the password is wrong, the account is locked out, or the email is not confirmed. AuthEndpoints returns one response for all three so that it does not reveal which one applies.
   - `429`: the rate limit rejected the request.

## Sign in with a password and Identity bearer tokens

Use this method for native and mobile clients, and for browsers that keep the token in `localStorage` or `sessionStorage`. Turn it on with `AddAuthEndpoints<TUser, TContext>(AuthEndpointsSignIn.IdentityBearer, ...)`, or compose `AddBearerAuthEndpoints` and `MapBearerAuthEndpoints`.

1. Send the same `LoginRequest` body to `POST /identity/login` without query flags.
2. On success, read `{ "tokenType", "accessToken", "expiresIn", "refreshToken" }` from the `200` body. Send the access token as `Authorization: Bearer <accessToken>`.
3. To get a new access token, send `{ "refreshToken" }` to `POST /identity/refresh`.

`useCookies=true` on this login sets a persistent application cookie instead of returning tokens. `useSessionCookies=true` sets a session cookie. The 2FA challenge is the same as cookie login: `401` with title `RequiresTwoFactor`.

::callout{icon="i-lucide-triangle-alert" color="warning"}
The bearer facade maps no `/csrfToken` route, but anonymous passkey ceremonies still need a CSRF token. Map a token endpoint in the host. See [Bearer auth](/modules/bearer-auth#antiforgery).
::

## Sign in with a password and a JWT

Turn on JWT with `o.Jwt.Enabled = true` and `o.Jwt.Configure`, or compose `AddJwtEndpoints` and `MapJwtAuthEndpoints`. Call `modelBuilder.UseRefreshToken()` on your `DbContext` and add a migration. See [JWT module](/modules/jwt).

1. Send `{ "email", "password", "twoFactorCode"?, "twoFactorRecoveryCode"? }` to `POST /auth/create` with `credentials: 'include'`. The `email` field also accepts a user name.

   ```js
   const { accessToken } = await fetch('/auth/create', {
     method: 'POST',
     credentials: 'include',
     headers: { 'Content-Type': 'application/json' },
     body: JSON.stringify({ email, password })
   }).then(r => r.json());
   ```

2. On success, the `200` body is `{ "accessToken", "tokenType": "Bearer" }`. The response also sets the `AuthEndpoints.Jwt.RefreshToken` cookie. That cookie is HttpOnly and `SameSite=Strict`. The refresh family ends 14 days after sign-in. Refreshing does not extend that cap.
3. To get a new access token, call `POST /auth/refresh` with the cookie and a CSRF token from `GET /auth/csrfToken`. The body is `{ "accessToken" }`, with no `tokenType`. Send one refresh at a time. A second use of the same refresh token revokes the whole family.

`create` returns these errors:

- `400 { "error": "invalid_request", ... }` when `email` or `password` is missing. This body is not problem details.
- `401` with detail `Invalid credentials.` for a wrong password, a lockout, or an unconfirmed email.
- `401` with the extension `requiresTwoFactor: true` when 2FA is on and the request has no code.

`refresh` returns `400 { "errors": [...] }` when the cookie is missing, expired, revoked, or reused. Reuse revokes the family. Native clients can set `JwtSessionOptions.RefreshTokenTransport` to `Body` so login and refresh return `refreshToken` and skip antiforgery. See [JWT module](/modules/jwt).

## Enter a two-factor code or a recovery code

These steps apply to all three password methods. To turn 2FA on, see [Turn on two-factor authentication](/guides/two-factor).

1. Send the email and password.
2. If the response is the 2FA challenge, ask the user for a 6-digit authenticator code or a recovery code. Cookie and Identity bearer login return title `RequiresTwoFactor`. JWT `create` returns the extension `requiresTwoFactor: true`.
3. Send the same request again with `twoFactorCode` or `twoFactorRecoveryCode` added.

If the client already has the code, send it in the first request. A valid code succeeds in one round trip.

A wrong code on cookie or Identity bearer login returns `401` with detail `Invalid credentials.` JWT `create` returns detail `Invalid two factor code.` for a wrong authenticator code, and the Identity error description for a wrong recovery code.

### Remembered browsers

A persistent cookie login (`?useSessionCookies=false`) with a valid `twoFactorCode` sets the Identity two-factor remember-client cookie. Later password logins from that browser skip the 2FA challenge. These logins do not set the cookie:

- A session cookie login (the default).
- A login with `twoFactorRecoveryCode`. Each recovery code works once.
- JWT `POST /auth/create`.

To clear the cookie, send `POST /auth/manage/2fa` with `{ "forgetMachine": true }`, or call `POST /auth/logout`.

## Sign in with a passkey

On the password facade, set `Passkeys.ServerDomain`. That maps these routes under `/auth/passkeys`, and it also maps `POST /passkeys/register`. Login without that register route is in [Passkeys](/modules/passkeys#map). To finish in JWT, set `Session` to `Jwt` on the facade, or pass `AuthEndpointsSession.Jwt` to `MapPasskeySignInEndpoints`. See [Sign-in completers](/concepts/security-model#sign-in-completers-write-the-session).

::callout{icon="i-lucide-triangle-alert" color="warning"}
Passkey sign-in skips two-factor authentication. A user who turned on 2FA can sign in with a passkey alone.
::

Send `credentials: 'include'` and the CSRF header on both requests. The ceremony state lives in a cookie.

1. Get request options from `POST /auth/passkeys/requestOptions`. Send `{}` for a discoverable credential, or `{ "email" }` to sign in identifier-first. An email lets the response reveal through `allowCredentials` that the account has passkeys.
2. Call `navigator.credentials.get`. If the user cancels, stop.
3. Send the credential to `POST /auth/passkeys/login` with `{ "credentialJson" }`. A cookie session sets the application cookie. Add `?useSessionCookies=false` for a persistent cookie. `useCookies` is ignored on that session. A map that does not pass a session uses the Identity bearer completer unless a query flag selects a cookie. See [Responses and errors](/modules/errors#passkeys).

   ```js
   const headers = { 'Content-Type': 'application/json', 'RequestVerificationToken': csrfToken };

   const options = await fetch('/auth/passkeys/requestOptions', {
     method: 'POST', credentials: 'include', headers, body: '{}'
   }).then(r => r.json());

   const credential = await navigator.credentials.get({
     publicKey: PublicKeyCredential.parseRequestOptionsFromJSON(options)
   });

   const response = await fetch('/auth/passkeys/login', {
     method: 'POST', credentials: 'include', headers,
     body: JSON.stringify({ credentialJson: JSON.stringify(credential) })
   });
   ```

4. Check the response:
   - `200` with an empty body and a cookie: the user is signed in.
   - `200` with `{ "accessToken", "tokenType" }` and a refresh cookie: the JWT completer signed the user in.
   - `401` with detail `Invalid credentials.`: the account is locked out or the email is not confirmed.
   - `400` with title `Invalid Credential`: the assertion failed or `credentialJson` was empty.
   - `400` validation problem `InvalidPasskeyState`: no ceremony was underway. Start again from step 1.

## Sign in with GitHub or Google

Set up the packages and routes as in [Register with GitHub or Google](/guides/registration#register-with-github-or-google). The same callback signs users in.

1. Send the browser to the login route with a top-level navigation:

   ```js
   window.location.assign('/auth/external/login/google?returnUrl=' + encodeURIComponent('/dashboard'));
   ```

2. The callback signs in a user who already has this provider login. It refuses a local user with the same email and no link, with the error `auto_link_disabled`. With `AutoLinkByEmail` set to `true`, it links that user only when the provider email is verified and the local email is confirmed.
3. On success, the default session is a `302` to `returnUrl` with the application cookie. The cookie is persistent because `IsPersistent` defaults to `true`. Pass `AuthEndpointsSession.Jwt` to set the JWT refresh cookie, then call `POST /auth/refresh` with a CSRF token. Body transport throws at map time. Pass `AuthEndpointsSession.IdentityBearer` to write the token body instead of redirecting. See [Sign-in completers](/concepts/security-model#sign-in-completers-write-the-session).

`returnUrl` must be a rooted local path, or an absolute URL whose origin is in `AllowedReturnUrlOrigins`. Any other value falls back to `DefaultReturnUrl`.

::callout{icon="i-lucide-triangle-alert" color="warning"}
OAuth sign-in skips two-factor authentication with both built-in completers.
::

## Sign in with an emailed code

Call `AddEmailCodeEndpoints` and map `MapEmailCodeEndpoints`. The password facade does not map these routes. The steps, the magic link, and sign-up are in [Sign in with an emailed code](/guides/email-code).

`POST /identity/emailCode/send` and `POST /identity/emailCode/verify` do not use a CSRF token. Verify uses the `AuthEndpoints.Login` rate limit. When the user has two-factor authentication on and `RequireTwoFactor` is `true` (the default), verify returns `401` with title `RequiresTwoFactor` until the body includes `twoFactorCode` or `twoFactorRecoveryCode`.

## Help a user who cannot sign in

- **Forgotten password.** `POST /auth/forgotPassword` always returns `200`. AuthEndpoints sends mail only to a confirmed account. See [Reset a forgotten password](/guides/reset-password).
- **Lost authenticator.** The user signs in with a recovery code instead of a TOTP code.
- **Locked out.** Lockout uses Identity's defaults. Change them with `ConfigureIdentity`. See [Configuration options](/modules/configuration).
- **Unconfirmed email.** The user opens the confirmation link first. See [Register users](/guides/registration).

## What sign-in does not support

AuthEndpoints does not include these features:

- Two-factor codes by SMS. Identity has an email token provider, but no endpoint exposes it as a second factor. An emailed one-time code is a first factor. See [Sign in with an emailed code](/guides/email-code).
- A passkey as a second factor after a password. Passkeys are a first factor only.
- Built-in Apple or Microsoft providers.
- An endpoint that lists or revokes a user's other sessions.
- An admin endpoint that unlocks an account.
