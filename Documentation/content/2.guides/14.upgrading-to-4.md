4.0 is the integration line for the next major release. Later parts append rows to this page. Package versions stay at 3.4.1 until that release ships.

## B3 — Email-code table gains Purpose

Hosts that call `UseEmailCodes()` add an EF migration and apply it before deploying. The library does not ship a `Migrations` folder.

The model adds `Purpose` (`int`, not null, default `0`) on `AuthEndpoints.AuthEndpointsEmailCodes`. It drops the index on `(EmailHash, CreatedAt)` and adds `(EmailHash, Purpose, CreatedAt)`, named `IX_AuthEndpointsEmailCodes_EmailHash_Purpose_CreatedAt`. Existing rows default to sign-in (`0`).

```bash
dotnet ef migrations add AuthEndpoints4 --project YourDataProject --startup-project YourHost
```

## B4 — Email-code messages include ReAuth

`EmailCodePurpose` gains `ReAuth` (`2`). `IEmailCodeSender<TUser>` implementations that switch on purpose handle `ReAuth`: the message is "confirm it's you", not a sign-in. `LinkUrl` is null. Sign-up stays `SignUp` (`1`). Those rows are still stored as sign-in.

## B5 — Confirm identity accepts an email code

`ConfirmIdentityRequest` gains `EmailCode`. `POST /confirmIdentity` accepts exactly one of `password`, `twoFactorCode`, `twoFactorRecoveryCode`, `credentialJson`, or `emailCode`. The `400` body is:

`Provide exactly one of Password, TwoFactorCode, TwoFactorRecoveryCode, CredentialJson, or EmailCode.`

Match that response on status. A password, authenticator, or passkey user who posts only `emailCode` gets `400` with title `EmailCodeProofUnavailable` when step-up by email is not offered.

## B6 — authMethods adds emailCode

`AuthMethodsResponse` gains `bool EmailCode` as the last constructor argument. JSON responses include `emailCode`. On `MapAccountManagementEndpoints` and `MapReAuthEndpoints` it is true when email-code step-up is registered and available for that user. The frozen `AddAuthEndpoints` / `MapAuthEndpoints` facade keeps `emailCode` false and does not map `POST /confirmIdentity/emailCode/send`. `ReAuthEndpoints<TUser>.AuthMethods(ClaimsPrincipal, UserManager<TUser>)` still forwards with `EmailCode` false.

## B13 — Email-code cooldown and send cap are per purpose

`ResendCooldown` and `MaxSendsPerEmail` apply per stored purpose. A step-up send does not supersede a sign-in code, and it does not consume that address's sign-in cooldown or send cap. The reverse is also true. No migration beyond B3.

## B17 — Per-method sign-in completers are obsolete

Removed in 5.0. An explicitly registered 3.x completer still runs when the sign-in map does not pass `session` or `completer`.

| 3.x | 4.0 |
| --- | --- |
| `IEmailCodeSignInCompleter<TUser>` / `EmailCodeSignInContext` | `ISignInCompleter<TUser>` / `SignInCompletionContext` |
| `AddEmailCodeSignInCompleter<TUser, TCompleter>()` | `AddSignInCompleter<TUser, TCompleter>(name)` |
| `IPasskeySignInCompleter<TUser>` / `PasskeySignInCompletionContext` | same keyed completer |
| `AddPasskeySignInCompleter<TUser, TCompleter>()` | `AddSignInCompleter<TUser, TCompleter>(name)` |
| `IExternalLoginCompleter<TUser>` | still the external callback; obsolete, not rewired yet |
| `ExternalAuthBuilder.AddCompleter<TCompleter>()` | still replaces `IExternalLoginCompleter<TUser>` |
| `IdentityEmailCodeSignInCompleter`, `JwtEmailCodeSignInCompleter`, `IdentityPasskeySignInCompleter`, `JwtPasskeySignInCompleter`, `CookieExternalLoginCompleter`, `JwtExternalLoginCompleter` | built-in sessions below, except external |

`PasskeySignInKind` and `PasswordLoginMode` stay. With no `session` or `completer` argument, email-code verify and passkey register/login keep the Identity bearer completer, and password login stays on `PasswordSignInAsync`.

### Pick a built-in session

`AuthEndpointsSession` selects a keyed completer registered by the library:

| Session | Name | Registered by | Result |
| --- | --- | --- | --- |
| `Cookie` | `SignInCompleters.Cookie` | `AddAuthEndpointsIdentity`, `AddPasswordEndpoints`, or `AddEmailCodeEndpoints` | Application cookie. Passkey register returns `{ credentialId }`. |
| `IdentityBearer` | `SignInCompleters.IdentityBearer` | same | Identity bearer body, or an application cookie when `useCookies` / `useSessionCookies` is set. Passkey register returns the token body and does not add `credentialId`. |
| `Jwt` | `SignInCompleters.Jwt` | `AddJwtEndpoints` | `accessToken` + `tokenType`, refresh cookie `AuthEndpoints.Jwt.RefreshToken`. Passkey register does not add `credentialId`. |

```cs
identity.MapPasswordEndpoints<AppUser>(AuthEndpointsSession.Jwt);
identity.MapEmailCodeEndpoints<AppUser>(AuthEndpointsSession.IdentityBearer);
account.MapPasskeySignInEndpoints<AppUser>(AuthEndpointsSession.Jwt);
```

Pass `AuthEndpointsSession` for passkey sign-in. `MapPasskeySignInEndpoints<TUser>(string?)` is still the confirm-email endpoint name. A call such as `MapPasskeySignInEndpoints<AppUser>("MySession")` or `MapPasskeySignInEndpoints<AppUser>(SignInCompleters.Jwt)` does not select that completer. When the string matches a registered completer name, map time logs a warning on the `AuthEndpoints` category and still uses the default completer. The named overload takes the completer and the confirm-email name (`null` uses the default name): `MapPasskeySignInEndpoints<AppUser>(SignInCompleters.Jwt, confirmEmailEndpointName: null)`.

`SignInCompletionOptions.Default` applies when `MapPasswordEndpoints()`, `MapEmailCodeEndpoints`, or `MapPasskeySignInEndpoints` is called with no session and no completer name. An explicit `PasswordLoginMode` beats `Default` and keeps that 3.x handler (`Cookie`, `IdentityBearer`, or `None`). `MapCookieAuthEndpoints`, `MapBearerAuthEndpoints`, `MapIdentityManagementApi`, and `MapPasskeyEndpoints` keep the 3.x choice. `AddAuthEndpoints` / `MapAuthEndpoints` ignore `Default` everywhere, including email-code verify.

### Custom completer

```cs
builder.Services.AddSignInCompleter<AppUser, MySignInCompleter>("MySession");
builder.Services.Configure<SignInCompletionOptions>(o => o.Default = "MySession");
```

Or pass `"MySession"` to the sign-in map. A name passed to the map wins over an explicitly registered 3.x completer. The 3.x registration wins over `SignInCompletionOptions.Default` when the map passes no name. Calling `AddSignInCompleter` again for the same user and name replaces that registration. The name is checked for the user type being mapped. A completer registered for another user fails at map time. The built-in `Cookie`, `IdentityBearer`, and `Jwt` names apply to every user type.

The completer runs only after the method has accepted the proof. Failures never call it.

`SignInCompletionContext.UsedTwoFactor` is true when password sign-in presented a valid authenticator or recovery code in this request. Cookie and Identity bearer completers add an `amr` claim of `mfa` when it is set, and `pwd` otherwise. A remembered two-factor client stays `pwd`.

External callbacks still use `IExternalLoginCompleter<TUser>`. `AddCompleter<T>()` still replaces that registration. They are obsolete so a later release can move them onto `ISignInCompleter<TUser>`; this change does not switch the external callback.

## Per-session and shared routes

No breaking change. `AddAuthEndpoints` / `MapAuthEndpoints` stay on the 3.4.1 route set, including antiforgery and rate limits. `MapIdentityManagementApi`, `MapCookieAuthEndpoints`, `MapBearerAuthEndpoints`, `MapJwtAuthEndpoints`, `MapPasskeyEndpoints`, `MapPasswordEndpoints`, `MapEmailCodeEndpoints`, and `MapPasskeySignInEndpoints` keep their names, signatures, and routes.

`MapPasskeySignInEndpoints` still maps `requestOptions`, `register/options`, `register`, and `login`, and still ensures confirm-email. Shrinking that 3.4 map would be a breaking change. Hosts that want the split call the new maps. `AddPasskeyEndpoints` remains the full set and calls the finer `Add*` methods.

Routes that finish in a completer are mapped once per session. The others are mapped once. Passkey `POST /passkeys/requestOptions` finishes the ceremony on that session's login route, so it is mapped per session with login, not on the shared map.

| Map | Add | Routes | Where |
| --- | --- | --- | --- |
| `MapPasswordSignInEndpoints` | `AddPasswordSignInEndpoints` | `POST /login` | per session |
| `MapEmailCodeSignInEndpoints` | `AddEmailCodeSignInEndpoints` | `POST /emailCode/verify` | per session |
| `MapPasskeySignInEndpoints` | `AddPasskeySignInEndpoints` | `POST /passkeys/requestOptions`, `POST /passkeys/login` (the 3.4 method also still maps `register/options` and `register`) | per session |
| `MapPasskeySignUpEndpoints` | `AddPasskeySignUpEndpoints` | `POST /passkeys/register` | per session |
| `MapCookieSessionEndpoints` | `AddCookieSessionEndpoints` | `POST /logout`, `GET /csrfToken` | per session |
| `MapBearerSessionEndpoints` | `AddBearerSessionEndpoints` | `POST /refresh`, `POST /logout` | per session |
| `MapJwtSessionEndpoints` | `AddJwtEndpoints` | `POST /refresh`, `GET /verify`, `POST /logout`, `GET /csrfToken` | per session |
| `MapPasswordSignUpEndpoints` | `AddPasswordSignUpEndpoints` | `POST /register` (and confirm-email when that name is new) | shared |
| `MapPasswordRecoveryEndpoints` | `AddPasswordRecoveryEndpoints` | `POST /forgotPassword`, `POST /resetPassword` | shared |
| `MapEmailCodeSendEndpoints` | `AddEmailCodeSendEndpoints` | `POST /emailCode/send` | shared |
| `MapPasskeyRegisterOptionsEndpoints` | `AddPasskeyRegisterOptionsEndpoints` | `POST /passkeys/register/options` | shared |
| `MapAccountManagementEndpoints` | `AddAccountManagementEndpoints` | manage and confirm-identity | shared |
| `MapPasskeyManagementEndpoints` | `AddPasskeyManagementEndpoints` | passkey credential management | shared |
| `MapConfirmEmailEndpoints` | `AddAccountAbuseRateLimiting` | `GET /confirmEmail`, `POST /resendConfirmationEmail` | shared |

`MapSignInEndpoints<TUser>(AuthEndpointsSession)` maps the per-session routes for modules that are registered, plus that session's routes. It logs a warning when no sign-in module is registered. Cookie and Identity bearer password login is `POST /login`. JWT password login is `POST /create`. `MapSharedAuthEndpoints<TUser>(sharedPath)` maps the shared routes once. Null `sharedPath` uses the current builder (the app root when called on the app). Each `Map*` returns `IEndpointConventionBuilder`.

`MapSignInEndpoints` maps passkey register on the session prefix and does not map confirm-email. The register handler still writes the confirmation link with the shared confirm-email endpoint name. Mapping passkey register without `MapSharedAuthEndpoints` (or `MapConfirmEmailEndpoints`) leaves that link pointing at a route that was never mapped. `MapPasskeySignUpEndpoints` maps confirm-email itself when that name is new.

```cs
app.MapGroup("/web").MapSignInEndpoints<AppUser>(AuthEndpointsSession.Cookie);
app.MapGroup("/app").MapSignInEndpoints<AppUser>(AuthEndpointsSession.Jwt);
app.MapSharedAuthEndpoints<AppUser>();
```

Confirm-email keeps one endpoint name, so it is mapped with the shared routes and not under each session prefix. Password sign-in (`POST /login` or `POST /create`) records that password sign-in is mapped. Sign-up and recovery do not.

## B21 — JWT refresh rotation and body transport

Cookie-mode refresh detects reuse. Presenting a refresh token that was already rotated revokes every token in that family, including the successor. Two callers that refresh with the same token at the same time are both signed out. Serialize refresh calls so only one request presents a given token.

Each family has an absolute lifetime, measured from the original sign-in. The default is 14 days, the same as `JwtSessionOptions.RefreshTokenLifetime`. Rotation cannot extend it. A refresh after the cap returns `400`. Set `AbsoluteLifetime` when a session should outlive that window. A successor then expires at the earlier of "now plus `RefreshTokenLifetime`" and the family's absolute end.

Refresh tokens stay bound to the user's security stamp. A password change, reset, or `UpdateSecurityStampAsync` revokes the family. Logout revokes the family on the server. Deleting the cookie does not.

Hosts that call `UseRefreshToken()` add a migration and apply it before deploying. The model adds `AbsoluteExpiresAt` (non-null datetime) on `AuthEndpoints.AuthEndpointsRefreshTokens`. Backfill existing rows from `ExpiresAt` so a stored token cannot outlive the expiry it already has.

```bash
dotnet ef migrations add AuthEndpointsRefreshAbsoluteLifetime --project YourDataProject --startup-project YourHost
```

### Refresh token in the JSON body

`JwtSessionOptions.RefreshTokenTransport` defaults to `Cookie`. `Body` is for native and CLI clients.

```cs
builder.Services.AddJwtEndpoints<AppUser, AppDbContext>(jwt =>
{
    jwt.Issuer = "https://example.com";
    jwt.Audience = "https://example.com";
    jwt.SigningOptions.SymmetricKey = key;
});
builder.Services.Configure<JwtSessionOptions>(session =>
{
    session.RefreshTokenTransport = RefreshTokenTransport.Body;
});
```

In body mode, `POST /create`, email-code `POST /emailCode/verify`, passkey register and login, and `POST /refresh` include `refreshToken`. `POST /refresh` and `POST /logout` accept `{ "refreshToken" }`. Those two routes do not require antiforgery, and `GET /csrfToken` is not mapped. Cookie mode keeps the HttpOnly cookie `AuthEndpoints.Jwt.RefreshToken`, antiforgery on refresh and logout, and no `refreshToken` field in the JSON. `GET /verify` stays `204` and does not return a refresh token.

`IdentityBearer` refresh tokens are unchanged. They are self-contained, have no reuse detection, and end only when the security stamp changes.

External browser sign-in still redirects and does not put a refresh token in the URL. Use cookie transport for that session.
