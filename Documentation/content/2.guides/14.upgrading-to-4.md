4.0 is the integration line for the next major release. Later parts append rows to this page. Package versions stay at 3.4.1 until that release ships.

## B17 — Per-method sign-in completers are obsolete

Removed in 5.0. An explicitly registered 3.x completer still runs when the sign-in map does not pass `session` or `completer`.

| 3.x | 4.0 |
| --- | --- |
| `IEmailCodeSignInCompleter<TUser>` / `EmailCodeSignInContext` | `ISignInCompleter<TUser>` / `SignInCompletionContext` |
| `AddEmailCodeSignInCompleter<TUser, TCompleter>()` | `AddSignInCompleter<TUser, TCompleter>(name)` |
| `IPasskeySignInCompleter<TUser>` / `PasskeySignInCompletionContext` | same keyed completer |
| `AddPasskeySignInCompleter<TUser, TCompleter>()` | `AddSignInCompleter<TUser, TCompleter>(name)` |
| `IExternalLoginCompleter<TUser>` | still the external callback; obsolete, not rewired yet |
| `ExternalAuthBuilder.AddCompleter<TCompleter>()` | still replaces `IExternalLoginCompleter<TUser>` |
| `IdentityEmailCodeSignInCompleter`, `JwtEmailCodeSignInCompleter`, `IdentityPasskeySignInCompleter`, `JwtPasskeySignInCompleter`, `CookieExternalLoginCompleter`, `JwtExternalLoginCompleter` | built-in sessions below, except external |

`PasskeySignInKind` and `PasswordLoginMode` stay. With no `session` or `completer` argument, email-code verify and passkey register/login keep the Identity bearer completer, and password login stays on `PasswordSignInAsync`.

### Pick a built-in session

`AuthEndpointsSession` selects a keyed completer registered by the library:

| Session | Name | Registered by | Result |
| --- | --- | --- | --- |
| `Cookie` | `SignInCompleters.Cookie` | `AddAuthEndpointsIdentity`, `AddPasswordEndpoints`, or `AddEmailCodeEndpoints` | Application cookie. Passkey register returns `{ credentialId }`. |
| `IdentityBearer` | `SignInCompleters.IdentityBearer` | same | Identity bearer body, or an application cookie when `useCookies` / `useSessionCookies` is set. Passkey register returns the token body and does not add `credentialId`. |
| `Jwt` | `SignInCompleters.Jwt` | `AddJwtEndpoints` | `accessToken` + `tokenType`, refresh cookie `AuthEndpoints.Jwt.RefreshToken`. Passkey register does not add `credentialId`. |

```cs
identity.MapPasswordEndpoints<AppUser>(AuthEndpointsSession.Jwt);
identity.MapEmailCodeEndpoints<AppUser>(AuthEndpointsSession.IdentityBearer);
account.MapPasskeySignInEndpoints<AppUser>(
    SignInCompleters.Jwt,
    confirmEmailEndpointName: null);
```

`MapPasskeySignInEndpoints<TUser>(string?)` is still the confirm-email endpoint name. The completer overload takes the name and the confirm-email name (`null` uses the default name).

`SignInCompletionOptions.Default` applies when `MapPasswordEndpoints`, `MapEmailCodeEndpoints`, or `MapPasskeySignInEndpoints` is called with no name. `MapCookieAuthEndpoints`, `MapBearerAuthEndpoints`, `MapIdentityManagementApi`, and `MapPasskeyEndpoints` keep the 3.x choice.

### Custom completer

```cs
builder.Services.AddSignInCompleter<AppUser, MySignInCompleter>("MySession");
builder.Services.Configure<SignInCompletionOptions>(o => o.Default = "MySession");
```

Or pass `"MySession"` to the sign-in map. A name passed to the map wins over an explicitly registered 3.x completer. The 3.x registration wins over `SignInCompletionOptions.Default` when the map passes no name. Calling `AddSignInCompleter` again for the same user and name replaces that registration.

The completer runs only after the method has accepted the proof. Failures never call it.

External callbacks still use `IExternalLoginCompleter<TUser>`. `AddCompleter<T>()` still replaces that registration. They are obsolete so a later release can move them onto `ISignInCompleter<TUser>`; this change does not switch the external callback.
