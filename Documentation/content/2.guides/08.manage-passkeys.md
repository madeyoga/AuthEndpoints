A signed-in user manages passkeys under `/account/passkeys`. Adding, renaming, and removing a passkey, and requesting creation options, require a fresh ReAuth proof for that same user. The caller must already be signed in with the application cookie, an Identity bearer token, or a JWT. A ReAuth cookie or `X-AuthEndpoints-Reauth` token by itself is not a sign-in: those requests return `401`. A signed-in caller who skips step-up, or sends a proof issued to someone else, gets `403` on the changes.

CSRF depends on how that sign-in was presented:

| Sign-in | CSRF on add, rename, remove, and creation options |
| --- | --- |
| Application cookie | Required. Send `RequestVerificationToken`. |
| Identity bearer or JWT in `Authorization: Bearer` | Skipped, when the access token is not also read from a cookie. |
| Access token stored in a cookie and read in `OnMessageReceived` | Required, including when the header is present as well. |

The sample below is the cookie stack. Send `credentials: 'include'` on every cookie request. Identity bearer and JWT callers send `Authorization: Bearer` and the ReAuth header, and omit the CSRF header unless the access token comes from a cookie. To create a new account with a passkey, see [Register users](/guides/registration#register-with-a-passkey) instead. Anonymous passkey register and login always require a CSRF token. See [Passkeys module](/modules/passkeys).

::callout{icon="i-lucide-info"}
Signed-in passkey management works on 3.1.0. The 3.1.0 bug affects only anonymous passkey registration and sign-in when JWT is not turned on. Upgrade to 3.1.1 to fix those. See [Register users](/guides/registration#register-with-a-passkey).
::

| Task | Endpoint | ReAuth | CSRF |
| --- | --- | --- | --- |
| Get creation options | `POST /account/passkeys/creationOptions` | Yes | Cookie session, or a token read from a cookie |
| Add a passkey | `POST /account/passkeys/` | Yes | Cookie session, or a token read from a cookie |
| List passkeys | `GET /account/passkeys/` | No | No |
| Rename a passkey | `PATCH /account/passkeys/` | Yes | Cookie session, or a token read from a cookie |
| Remove a passkey | `DELETE /account/passkeys/{credentialIdUrl}` | Yes | Cookie session, or a token read from a cookie |

## Add a passkey

1. Complete step-up. See [Require step-up before sensitive actions](/guides/step-up).
2. Get creation options from `POST /account/passkeys/creationOptions`. The options are for the signed-in user.
3. Call `navigator.credentials.create`.
4. Send `POST /account/passkeys/` with `{ "credentialJson", "name"? }`. AuthEndpoints trims `name`. A name longer than 200 characters returns a `400` validation problem with the key `Name`.

   ```js
   const headers = { 'Content-Type': 'application/json', 'RequestVerificationToken': csrfToken };

   const options = await fetch('/account/passkeys/creationOptions', {
     method: 'POST', credentials: 'include', headers
   }).then(r => r.json());

   const credential = await navigator.credentials.create({
     publicKey: PublicKeyCredential.parseCreationOptionsFromJSON(options)
   });

   const added = await fetch('/account/passkeys/', {
     method: 'POST', credentials: 'include', headers,
     body: JSON.stringify({ credentialJson: JSON.stringify(credential), name: 'Work laptop' })
   }).then(r => r.json()); // { credentialId, displayName, createdAt }
   ```

5. Check the response:
   - `200 { "credentialId", "displayName", "createdAt" }`: the passkey is stored.
   - `400` validation problem `UserMismatch`: the passkey belongs to a different user.
   - `400` validation problem `InvalidPasskeyState`: no ceremony was underway. Start again from step 2.
   - `400` with a detail that starts with "Could not add the passkey": the attestation failed.

## List passkeys

Send `GET /account/passkeys/`. The response is `{ "passkeys": [{ "credentialId", "displayName", "createdAt" }] }`. `credentialId` is Base64Url.

## Rename a passkey

Complete step-up, then send `PATCH /account/passkeys/` with `{ "id": "<credentialId>", "newName": "..." }`. AuthEndpoints trims `newName`. A name longer than 200 characters returns a `400` validation problem with the key `Name`, and the stored name stays as it was. A value that is only whitespace clears the name. The success response is `200` with an empty body. An unknown id returns `404`. An id that is not valid Base64Url returns a `400` validation problem `InvalidCredentialId`.

## Remove a passkey

Complete step-up, then send `DELETE /account/passkeys/<credentialId>`. The response is `200` with an empty body. An unknown id returns `404`. An id that is not valid Base64Url returns a `400` validation problem `InvalidCredentialId`.

The delete is refused when this passkey is the user's only sign-in method: the account has no password and no external login, and this is the only passkey. The response is a `400` validation problem with the key `LastSignInMethod` and the detail `Cannot remove the last sign-in method.` Two-factor authentication is not a sign-in method. An account with a password, an external login, or another passkey can delete this one.
