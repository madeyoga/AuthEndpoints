AuthEndpoints keeps its rules (cooldowns, attempt limits, rotation, reuse detection, consent) in its own services, and reads and writes rows only through store interfaces. The EF Core packages implement every interface. To keep data elsewhere, register your own implementation instead.

| Package | Registers |
| --- | --- |
| `AuthEndpoints.EntityFrameworkCore` | `.AddEntityFrameworkStores<TContext>()` on `AddAuthEndpoints`: Identity's EF Core user (and role) stores, and the AuthEndpoints stores below |
| `AuthEndpoints.OpenIddict.EntityFrameworkCore` | `.AddEntityFrameworkStores<TContext>()` on `AddOAuthServer`: OpenIddict's EF Core stores, and the OAuth server stores below |

## Every store

### Users and roles (ASP.NET Core Identity)

AuthEndpoints signs users in through `UserManager<TUser>` and `SignInManager<TUser>`, so users live wherever Identity's stores put them. Register an `IUserStore<TUser>` (and an `IRoleStore<TRole>` with `AddRoles<TRole>()`) with Identity, for example `builder.Services.AddAuthEndpoints<AppUser>().Identity.AddUserStore<MyUserStore>()`. Implement the optional Identity store interfaces each feature uses:

| Feature | Identity store interfaces |
| --- | --- |
| Password sign-in and recovery | `IUserPasswordStore<TUser>`, `IUserEmailStore<TUser>`, `IUserSecurityStampStore<TUser>`, `IUserLockoutStore<TUser>` |
| Two-factor | `IUserTwoFactorStore<TUser>`, `IUserAuthenticatorKeyStore<TUser>`, `IUserTwoFactorRecoveryCodeStore<TUser>` |
| Passkeys | `IUserPasskeyStore<TUser>` |
| GitHub, Google, and other external providers | `IUserLoginStore<TUser>` |
| Roles on tokens and `RequireRole` | `IUserRoleStore<TUser>`, `IRoleStore<TRole>` |

`TUser` must still derive from `IdentityUser<TKey>`: AuthEndpoints reads the key type from it.

### AuthEndpoints

| Interface | Needed by | Rows |
| --- | --- | --- |
| `IEmailCodeStore` | `AddEmailCode`, `AddEmailCodeEndpoints` | `EmailCodeEntry` |
| `IRefreshTokenStore` | `AddJwt`, `AddJwtEndpoints` | `RefreshToken` |
| `IActiveSessionStore` | `AddActiveSessions` | `ActiveSession` |
| `IUserCreateFailureHandler<TUser>` | Optional. Email-code sign-up asks it whether an exception from `UserManager.CreateAsync` was a refused insert, such as two requests creating the same account | none |

### OAuth server (AuthEndpoints.OpenIddict)

| Interface | Holds |
| --- | --- |
| `IOpenIddictApplicationStore<>`, `IOpenIddictAuthorizationStore<>`, `IOpenIddictScopeStore<>`, `IOpenIddictTokenStore<>` | OpenIddict's clients, grants, scopes, and tokens. Register them through `oauth.OpenIddict.AddCore(…)`, as [OpenIddict documents](https://documentation.openiddict.com/) |
| `IOAuthRequestStore<TKey>` | Pending consent requests |
| `IOAuthDeveloperAppStore<TKey>` | Developer app rows: who owns each app, and whether it may be used |
| `IOAuthServerQueries` | Bulk reads of OpenIddict's data: a user's live grants, an app's valid grants, and redirect URIs for many clients. Build each grant with `OAuthAuthorizationRecord.FromStore`, or `ReadAsync` through OpenIddict's authorization manager |
| `IOAuthServerEventTransactions` | Optional. Holds audit events until your transaction commits |
| `IOAuthAuthorizationRefresher` | Optional. Reloads a grant after OpenIddict reports a concurrency failure |

`OAuthStoreLimits` holds the longest value the server writes to each length-limited column.

## What a store must do

Each interface method's XML docs say exactly what it must do. The rules they share:

- **One method, one atomic operation.** A method such as `IEmailCodeStore.TryConsumeAsync`, `IRefreshTokenStore.TryRotateAsync`, or `IOAuthRequestStore<TKey>.TryConsumeAsync` decides a race: of two concurrent calls, exactly one returns `true`. Use a conditional update (`UPDATE … WHERE ConsumedAt IS NULL`), a compare-and-swap, or a transaction, never a read followed by a separate write.
- **Writes change only their own fields.** `IOAuthDeveloperAppStore<TKey>` has one method per change (approve, disable, rename, rotate the secret) instead of saving a whole row, so a stale copy can never undo a concurrent disable.
- **Honor the cancellation token you get.** AuthEndpoints passes `CancellationToken.None` to refresh-token rotation and to the family revoke that reuse detection runs, so a client that disconnects cannot stop them halfway. Other methods get the request's token.
- **Secrets arrive hashed.** A store never sees a raw email code, magic-link token, or refresh token. Email addresses arrive hashed, except `EmailCodeEntry.SignupEmail`, which a sign-up row keeps so that the magic link can create the account.

## Register your stores

Register a store before the EF Core stores to replace just that one. The EF Core packages add each store only when none is registered yet:

```csharp
builder.Services.AddSingleton<IEmailCodeStore, RedisEmailCodeStore>();   // replaces the EF Core one
builder.Services.AddAuthEndpoints<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>()                            // users, refresh tokens, sessions
    .AddPassword()
    .AddEmailCode();
```

Without any EF Core package, register every store a feature needs:

```csharp
builder.Services.AddSingleton<IRefreshTokenStore, MyRefreshTokenStore>();
var auth = builder.Services.AddAuthEndpoints<AppUser>()
    .AddPassword()
    .AddJwt(jwt => { /* … */ });
auth.Identity.AddUserStore<MyUserStore>();
```

The OAuth server works the same way:

```csharp
var oauth = builder.Services.AddOAuthServer<AppUser>(options => { /* … */ });
oauth.OpenIddict.AddCore(core => { /* OpenIddict's stores */ });
builder.Services.AddScoped<IOAuthRequestStore<string>, MyOAuthRequestStore>();
builder.Services.AddScoped<IOAuthDeveloperAppStore<string>, MyOAuthDeveloperAppStore>();
builder.Services.AddScoped<IOAuthServerQueries, MyOAuthServerQueries>();
```

A missing store fails `MapAuthEndpoints` or `MapOAuthServer` at startup, with a message that names the interface. In Development, `WebApplication.Build()` validates services first, so its own error names the missing service.

## Test your stores

The repository runs one set of contract tests against both the EF Core stores and in-memory ones, including the races: concurrent consumes, reservations, rotations, and consent answers. Copy the abstract class for each interface you implement, and override one method that returns a store over your test's data:

| Interface | Contract tests |
| --- | --- |
| `IEmailCodeStore` | [`EmailCodeStoreContract`](https://github.com/madeyoga/AuthEndpoints/blob/main/tests/AuthEndpoints.Tests/StoreContracts/EmailCodeStoreContract.cs) |
| `IRefreshTokenStore`, `IActiveSessionStore` | [`RefreshTokenStoreContract`, `ActiveSessionStoreContract`](https://github.com/madeyoga/AuthEndpoints/blob/main/tests/AuthEndpoints.Tests/StoreContracts/RefreshTokenAndSessionStoreContracts.cs) |
| `IOAuthRequestStore<TKey>`, `IOAuthDeveloperAppStore<TKey>` | [`OAuthRequestStoreContract`, `OAuthDeveloperAppStoreContract`](https://github.com/madeyoga/AuthEndpoints/blob/main/tests/AuthEndpoints.OpenIddict.Tests/OAuthStoreContracts.cs) |

```csharp
public sealed class RedisEmailCodeStoreContract : EmailCodeStoreContract
{
    private readonly IConnectionMultiplexer _redis = ConnectionMultiplexer.Connect("localhost");

    protected override Task<IEmailCodeStore> NewStoreAsync() => Task.FromResult<IEmailCodeStore>(new RedisEmailCodeStore(_redis));
}
```

Return a new store instance from each call when your store holds per-request state, as a new request would get one. The race tests then run on separate instances. The in-memory stores next to the contracts are a small working example of each rule above.
