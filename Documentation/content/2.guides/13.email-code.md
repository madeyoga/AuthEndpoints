Email-code sign-in stays off until you enable it. The user receives a numeric code. A magic link and sign-up from an unknown address are separate switches, and both default to off.

The examples use `IdentityPath` `/identity`. Reference tables are in the [Email-code module](/modules/email-code).

## Turn it on

1. Map the entity and add a migration. `MapEmailCodeEndpoints` throws if `UseEmailCodes()` was not called.

   ```cs
   protected override void OnModelCreating(ModelBuilder builder)
   {
       base.OnModelCreating(builder);
       builder.UseEmailCodes();
   }
   ```

2. Register `IEmailCodeSender<TUser>` with your mail transport. In Development, if you register none, AuthEndpoints uses `DevelopmentEmailCodeSender<TUser>`, which writes the raw code to the log. Outside Development, startup fails while that sender, or no sender, is registered, unless `RequireSenderOutsideDevelopment` is `false`.
3. Enable the facade flag:

   ```cs
   builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(o =>
   {
       o.EmailCode.Enabled = true;
   });
   ```

   `AddEmailCodeEndpoints<TUser, TContext>` and `MapEmailCodeEndpoints<TUser>` do the same work without the facade. Map the two routes on the same group prefix you use for Identity.

`o.Jwt.Enabled` does not change the email-code completer. To issue a Simple JWT from verify, register `JwtEmailCodeSignInCompleter<TUser>` after `AddEmailCodeEndpoints`:

```cs
builder.Services.AddEmailCodeSignInCompleter<AppUser, JwtEmailCodeSignInCompleter<AppUser>>();
```

That completer needs `AddJwtEndpoints` and `modelBuilder.UseRefreshToken()`.

## Send a code

`POST /identity/emailCode/send` takes `{ "email" }`. A valid address returns `200`:

```json
{ "expiresInSeconds": 600, "resendAfterSeconds": 60 }
```

Those two numbers are `CodeLifetime` and `ResendCooldown` in whole seconds. The defaults are 10 minutes and 60 seconds.

The same `200` body is returned when the address is unknown, the account is locked out, the account is not eligible, the resend cooldown is active, the per-address send cap is reached, the sender throws, or issuing the row still fails with a SQL Server deadlock (error 1205), a MySQL deadlock (error 1213), a Postgres serialization failure (`40001`) or deadlock (`40P01`), or a SQLite busy or locked error (5 or 6). The store tries that insert twice. When the store call throws the same conflict, send tries the call twice. That is up to four attempts. An address that fails the email check returns `400` with a validation problem `InvalidEmail`.

Your sender receives `EmailCodeMessage<TUser>`:

| Property | Meaning |
| --- | --- |
| `Email` | The trimmed address from the request |
| `User` | The Identity user, or `null` when no user has that address |
| `Code` | The raw digits. They are not HTML-encoded |
| `LinkUrl` | `null` unless the magic link is on |
| `ExpiresAt` | UTC expiry |
| `Lifetime` | `CodeLifetime` |
| `Purpose` | `SignIn`, or `SignUp` when this send can create an account |

`POST /identity/emailCode/send` awaits `SendSignInCodeAsync`. Queue the message and return. A sender that waits on SMTP or HTTP makes a known address slower than an unknown one. Do not log `Code` or `LinkUrl`.

## Verify a code

`POST /identity/emailCode/verify` takes `{ "email", "code" }`. `code` is exactly `CodeLength` digits. The default length is 6.

The query flags choose the session. They match Identity bearer login, not cookie `LoginCookie`:

| Query | Result |
| --- | --- |
| Neither flag | Identity bearer token JSON. `accessToken` is present |
| `useCookies=true` | Persistent application cookie. The body is empty |
| `useSessionCookies=true` | Session application cookie. The body is empty |

A correct code for an eligible confirmed user returns `200`. Read the session, then call `GET /identity/manage/info` to confirm the account.

These `401` responses use problem details:

| Title | Detail | When |
| --- | --- | --- |
| `Unauthorized` | `Invalid or expired code.` | The code is wrong, expired, already used, over the attempt cap, or the account cannot sign in |
| `RequiresTwoFactor` | `Two-factor authentication is required.` | The user has two-factor authentication on, `RequireTwoFactor` is `true`, and the body has neither `twoFactorCode` nor `twoFactorRecoveryCode` |

Send `twoFactorCode` for a TOTP code, or `twoFactorRecoveryCode` for a recovery code. A missing second factor releases the reserved attempt and does not consume the row. A wrong TOTP keeps the attempt and does not consume the row. A recovery code is redeemed after the row is consumed. If redeem fails, the consume is cleared and the attempt stays. `GET /identity/emailCode/verify` is `405`.

## Create an account from the code

Set `AllowSignUp` to `true` inside `EmailCode.Configure` (or the `AddEmailCodeEndpoints` callback). An unknown address is then mailed with `Purpose` `SignUp`. The `200` send body does not change.

A correct code creates one user:

- `UserName` and `Email` are the trimmed address.
- `EmailConfirmed` is set to `true` before `CreateAsync`. Sign-up does not use the email-confirmation token provider, does not send `IEmailSender` confirmation mail, and does not set a password.
- The sign-in completer receives `EmailCodeSignInContext.IsNewUser` `true`. The HTTP body is still the session from the table above.

An address that already has a user stays on the sign-in path. `IsNewUser` is `false`. When that user is already confirmed, the existing password stays in place. An unconfirmed user follows `UnconfirmedAccounts`.

With `AllowSignUp` left at `false`, a correct code for an unknown address returns `401` and creates no user.

## Use a magic link

Set `MagicLink.Enabled` to `true` and set `LinkUri` to an absolute `http` or `https` URI that does not contain `#`. A rooted path such as `/auth/email-link` is accepted when `BuildLinkUrl` is set. Relative paths and protocol-relative URIs are rejected either way. In Production an absolute URI must use `https`, and its origin must be listed in `MagicLink.AllowedOrigins`.

The default `LinkUrl` is `LinkUri` plus `#token=` plus the token. Assign `MagicLink.BuildLinkUrl` to build a different URL. The method receives `EmailCodeLinkContext` (`Token` and `LinkUri`) and returns the raw URL. The token is not HTML-encoded.

The fragment is not sent to your server. The client reads `token` from the fragment and posts only that field:

```json
{ "token": "…" }
```

A body that includes `token` together with `email` or `code`, or that includes neither pair, returns `400` with validation problem `InvalidEmailCodeRequest` and the description `Provide an email and a numeric code.` A token-only body is `400` while `MagicLink.Enabled` is `false`, and the row is not consumed.

One successful verify consumes the row. A second verify of the same code or token returns `401`.

## Confirm an existing unconfirmed account

`UnconfirmedAccounts` defaults to `ConfirmAndResetCredentials`. If that user already has a password, an external login, or a passkey, verify removes those credentials and updates the security stamp before it confirms the email. If a removal fails, the response is `401` and the email stays unconfirmed.

Set `UnconfirmedAccounts` to `Reject` to return `401` instead, without confirming the email and without removing credentials. Send also skips mail for that account.

A new sign-up user is confirmed at creation and has no credentials to remove.

## Email-code sign-in with a cookie session

Skip password register and login when the emailed code is the only sign-in. Register Identity, the cookie session, account management, and email-code services, then map those three groups on one prefix. The full host is [Email-code only](/composables/recipes#email-code-only).

```cs
builder.Services.AddAuthEndpointsIdentity<AppUser, AppDbContext>(options =>
{
    options.User.RequireUniqueEmail = true;
});
builder.Services.AddCookieSessionEndpoints();
builder.Services.AddAccountManagementEndpoints();
builder.Services.AddEmailCodeEndpoints<AppUser, AppDbContext>(options =>
{
    options.AllowSignUp = true;
});

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.UseRateLimiter();
app.UseAntiforgery();

var identity = app.MapGroup("/identity");
identity.MapEmailCodeEndpoints<AppUser>();
identity.MapCookieSessionEndpoints<AppUser>();
identity.MapAccountManagementEndpoints<AppUser>();
```

That maps `POST /emailCode/send`, `POST /emailCode/verify`, `POST /logout`, `GET /csrfToken`, confirm-email, resend, `POST /confirmIdentity`, `POST /confirmIdentity/emailCode/send`, and the `/manage` routes, including `POST /manage/password`. It omits `POST /register`, `POST /login`, `POST /forgotPassword`, and `POST /resetPassword`. `POST /manage/password` returns `404` until password sign-in is mapped. `MapAccountManagementEndpoints` maps `POST /confirmIdentity/passkeyOptions` when `AddPasskeyEndpoints` was called.

Verify with `?useSessionCookies=true` or `?useCookies=true` so the response sets the application cookie. `POST /logout` clears that cookie.

::callout{icon="i-lucide-info" color="info"}
This composition maps `POST /confirmIdentity/emailCode/send`. A confirmed user with no password, authenticator, or passkey can confirm with `{ "emailCode" }` and then call `POST /manage/info` or `POST /manage/2fa`. The code lasts 5 minutes by default. Enabling 2FA or adding a passkey turns the proof off.
::

Call `modelBuilder.UseEmailCodes()` and migrate before `MapEmailCodeEndpoints`. 4.0 adds `Purpose` and replaces the `(EmailHash, CreatedAt)` index. Generate that migration before deploying. See [B3](/guides/upgrading-to-4#b3--email-code-table-gains-purpose).
