### AuthEndpoints

3.4.0 adds map methods you can call on their own. `MapIdentityManagementApi`, `MapCookieAuthEndpoints`, `MapBearerAuthEndpoints`, `MapJwtAuthEndpoints`, and `MapPasskeyEndpoints` stay, and each still maps the same routes as 3.3.0. `MapAuthEndpoints` keeps that default route set. Nothing in the public API was removed or renamed. This release adds no database migration.

The new maps are password (`MapPasswordEndpoints`), cookie and Identity bearer sessions (`MapCookieSessionEndpoints`, `MapBearerSessionEndpoints`), JWT create and session (`MapJwtPasswordEndpoints`, `MapJwtSessionEndpoints`), passkey sign-in and credential management (`MapPasskeySignInEndpoints`, `MapPasskeyManagementEndpoints`), shared confirm-email (`MapConfirmEmailEndpoints`), and account management (`MapAccountManagementEndpoints`). `AddPasswordEndpoints`, `AddCookieSessionEndpoints`, `AddBearerSessionEndpoints`, `AddAccountManagementEndpoints`, and `AddAuthEndpointsIdentity` register the services those maps use. `AddAccountAbuseRateLimiting` and `AddConfirmIdentityRateLimiting` are public.

When a `Map*` method runs and its `Add*` method was not called, AuthEndpoints writes a warning. The category is `AuthEndpoints`. The message is `{AddMethod} was not called before {MapMethod}.` The routes are still mapped. `MapConfirmEmailEndpoints` warns `AddAccountAbuseRateLimiting was not called before MapConfirmEmailEndpoints.` when that policy marker is missing.

Confirm-email is mapped once per endpoint name. The default name is `AuthEndpointsEndpointNames.ConfirmEmail<TUser>()`, which is `MapIdentityManagementApi-{TUser}-confirmEmail`. A later map with that same name leaves the first route in place. Pass a different `confirmEmailEndpointName` when two groups should each expose `GET /confirmEmail`.

`MapAccountManagementEndpoints` maps `POST /confirmIdentity/passkeyOptions` when `AddPasskeyEndpoints` was called. `MapIdentityManagementApi` still maps that route either way, so the 3.3.0 management set stays intact. `MapPasskeySignInEndpoints` maps confirm-email on the parent group when that name is new. `MapPasskeyEndpoints` does not map confirm-email.

`POST /confirmIdentity` still accepts a password, an authenticator code, a recovery code, or a passkey assertion. An emailed code is not a step-up proof in this release.

An email-code host can skip password register and login. See [Email-code sign-in with a cookie session](/guides/email-code#email-code-sign-in-with-a-cookie-session).

### Upgrading from 3.3.x

- Existing `Add*` and `Map*` calls keep their routes. No host change is required.
- Hosts coming from 3.3.0 follow the 3.3.1 `MagicLink.LinkUri` rule: an absolute `http` or `https` URI with no `#`. A rooted path such as `/auth/email-link` is accepted when `MagicLink.BuildLinkUrl` is set.
- A second confirm-email map that reuses the default endpoint name leaves the first route in place. `MapConfirmEmailEndpoints` returns a no-op builder in that case.
- A missing `Add*` is a warning in the `AuthEndpoints` log category. Register the matching `Add*` so rate limits, ReAuth schemes, and antiforgery are present.
