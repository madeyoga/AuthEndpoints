### AuthEndpoints

On a host with email-code sign-in only, `POST /confirmIdentity/emailCode/send` now returns `404` instead of `500`, and `authMethods.emailCode` goes from `true` to `false`. The send route and the `AuthEndpoints.ConfirmIdentity.EmailCode` rate-limit policy belong to email-code send. Sign-in alone left the route mapped without that policy, so each signed-in call to it returned `500`. `POST /confirmIdentity` with `{ "emailCode" }` on that host returns `400` with title `EmailCodeProofUnavailable` instead of `401`.

Hosts that want the step-up send call `AddEmailCodeSendEndpoints` or `AddEmailCodeEndpoints`.

No host change is required for apps that already add email-code send. This release adds no database migration.

On a password facade with `Passkeys.ServerDomain` set, an extra `MapCookieAuthEndpoints` throws `InvalidOperationException` with `Call AddPasswordEndpoints before MapCookieAuthEndpoints.` An extra `MapIdentityManagementApi` throws `Call AddPasswordEndpoints before MapPasswordEndpoints.` The throw happens when the map runs, on a JWT session and on a cookie session. `AddPasswordAuth` registers the passkey sign-in, sign-up, register-options, and management modules, and the passkey module itself. It does not register the password module. On a JWT session it also does not register the cookie-session module. `MapAccountManagementEndpoints` maps `POST /confirmIdentity/passkeyOptions` when that passkey module is registered. `MapIdentityManagementApi` and the 3.x facade always map that route.

No host change is required for a password facade that maps only `MapPasswordAuth`. This note adds no database migration.

### Passkey ceremonies

The anonymous ceremonies `POST /passkeys/requestOptions`, `POST /passkeys/register/options`, `POST /passkeys/register`, and `POST /passkeys/login` require an antiforgery token for a cookie session and for JWT with cookie refresh transport. Identity bearer and JWT with body refresh transport do not. `MapBearerAuthEndpoints` maps no `csrfToken` route, and JWT body refresh maps none, so those ceremonies no longer ask for a token the host does not issue.

A cookie session ceremony without a token still returns `400` with `Invalid or missing CSRF token.` JWT cookie refresh still requires the token from `GET /csrfToken`. Identity bearer and JWT body refresh complete passkey register and login without a token. `MapPasskeyEndpoints`, `MapPasskeySignInEndpoints`, and `MapPasskeySignUpEndpoints` with no session argument keep the token. Pass `AuthEndpointsSession.IdentityBearer` to omit it on those ceremonies. The bearer facade does.

3.x facade behaviour change: `AddAuthEndpoints` with `IdentityBearer` no longer requires antiforgery on `POST /account/passkeys/requestOptions`, `POST /account/passkeys/register/options`, `POST /account/passkeys/register`, and `POST /account/passkeys/login`. The 3.x cookie facade is unchanged.

Signed-in passkey changes (`POST /passkeys/creationOptions`, `POST /passkeys/`, `PATCH /passkeys/`, `DELETE /passkeys/{credentialIdUrl}`) still require antiforgery on every session. An `Authorization: Bearer` access token skips that check. Cookie callers, including `useCookies=true`, still send the token. A cookie host that calls `PATCH /passkeys/` or `DELETE /passkeys/{credentialIdUrl}` without a token receives `400` with `Invalid or missing CSRF token.`

The Identity ceremony state lives in the `TwoFactorUserIdScheme` cookie (`Identity.TwoFactorUserId`). That cookie is single-use state, not a credential, and clients must send it between the options call and the verify call.

No host change is required for Identity bearer or JWT body passkey clients on the anonymous ceremonies. Cookie and JWT cookie-refresh clients keep sending `RequestVerificationToken`. This note adds no database migration.
