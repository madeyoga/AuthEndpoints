### AuthEndpoints

On a host with email-code sign-in only, `POST /confirmIdentity/emailCode/send` now returns `404` instead of `500`, and `authMethods.emailCode` goes from `true` to `false`. The send route and the `AuthEndpoints.ConfirmIdentity.EmailCode` rate-limit policy belong to email-code send. Sign-in alone left the route mapped without that policy, so each signed-in call to it returned `500`. `POST /confirmIdentity` with `{ "emailCode" }` on that host returns `400` with title `EmailCodeProofUnavailable` instead of `401`.

Hosts that want the step-up send call `AddEmailCodeSendEndpoints` or `AddEmailCodeEndpoints`.

No host change is required for apps that already add email-code send. This release adds no database migration.

On a password facade with `Passkeys.ServerDomain` set, an extra `MapCookieAuthEndpoints` throws `InvalidOperationException` with `Call AddPasswordEndpoints before MapCookieAuthEndpoints.` An extra `MapIdentityManagementApi` throws `Call AddPasswordEndpoints before MapPasswordEndpoints.` The throw happens when the map runs, on a JWT session and on a cookie session. `AddPasswordAuth` registers the passkey sign-in, sign-up, register-options, and management modules, and the passkey module itself. It does not register the password module. On a JWT session it also does not register the cookie-session module. `MapAccountManagementEndpoints` maps `POST /confirmIdentity/passkeyOptions` when that passkey module is registered. `MapIdentityManagementApi` and the 3.x facade always map that route.

No host change is required for a password facade that maps only `MapPasswordAuth`. This note adds no database migration.

### Passkey ceremonies

Passkey ceremonies require an antiforgery token for a cookie session and for JWT with cookie refresh transport. Identity bearer and JWT with body refresh transport do not. `MapBearerAuthEndpoints` maps no `csrfToken` route, and JWT body refresh maps none, so those ceremonies no longer ask for a token the host does not issue.

A cookie session ceremony without a token still returns `400` with `Invalid or missing CSRF token.` JWT cookie refresh still requires the token from `GET /csrfToken`. Identity bearer and JWT body refresh complete passkey register and login without a token.

.NET 10 `SignInManager` stores the ceremony state in the `Identity.TwoFactorUserId` cookie. Clients keep that cookie between the options call and the register or login call.

Signed-in passkey changes follow the same session rule. When the filter is still attached, an `Authorization: Bearer` access token skips the check.

No host change is required for Identity bearer or JWT body passkey clients. Cookie and JWT cookie-refresh clients keep sending `RequestVerificationToken`. This note adds no database migration.
