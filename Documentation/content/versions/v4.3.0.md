### AuthEndpoints

**Caller kind.** `User.GetCallerKind()` returns a `CallerKinds` value: `person` for the Identity application cookie, an Identity bearer token, or an AuthEndpoints JWT; `delegated` for an OAuth access token a client uses for a person; or `api_key`. The kind is the `ae:caller` claim (`CallerKinds.ClaimType`). The built-in sign-in identities are recognized by their authentication type, so cookies and tokens issued before this release are people too, and nothing new is written into them. A host scheme sets `ae:caller` on the identities it creates; an identity from an unknown scheme has no kind. When a principal holds identities from several schemes, any kind other than `person` wins. `User.GetActingClientId()` reads the client from the RFC 8693 `act` claim of a delegated token. See [People and agents](/modules/callers).

**Routes for people only.** `RequireDirectPerson()`, on a route or in a policy (`DirectPersonRequirement`), gives `403` to delegated tokens, API keys, and identities of unknown kind.

**`RequireAuthEndpointsUser()` requires a direct person.** It now also adds `DirectPersonRequirement`. That covers the built-in password and profile, two-factor, passkey management, ReAuth, external sign-in, and session routes. They already authenticated only with the application cookie, Identity bearer, and JWT bearer schemes, so standard hosts see no change. A cookie or token whose principal the host tagged with another `ae:caller` value now gets `403` there.

**One handler per credential (opt-in).** `AddAnyCallerScheme()` registers the `AuthEndpoints.AnyCaller` policy scheme. An `Authorization` credential starting with `ApiKeyPrefix` goes to `ApiKeyScheme`, any other `Authorization` header to `BearerScheme` (default: JWT if registered, else Identity bearer), and a request without one to the application cookie. A request with an invalid token and a valid cookie gets `401`. The default scheme does not change.

No host change is required. This release adds no database migration.
