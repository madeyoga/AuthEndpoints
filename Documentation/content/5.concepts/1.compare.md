AuthEndpoints is a first-party auth API on top of ASP.NET Core Identity. Use it when you own the users. Use something else when you need an OAuth or OpenID Connect server, or when Microsoft's Identity API endpoints already cover the whole job.

## vs wiring Identity yourself

You still use Identity, EF Core, and your user type. AuthEndpoints maps the endpoints you would otherwise write: register, login, 2FA, password reset, passkeys, and GitHub or Google sign-in. You also get the hardening that hand-written endpoints often miss: rate limits, CSRF checks, and generic responses that do not reveal which emails exist.

## vs OpenIddict

OpenIddict is an OAuth 2 and OpenID Connect server. Use it when other apps sign in to you as a provider. AuthEndpoints is for your own web and mobile clients that call your own API. It issues first-party cookies or tokens. It is not a federation server.

## vs Identity API endpoints (`MapIdentityApi`)

Identity API endpoints give you a bearer-token first-party API. AuthEndpoints covers that job and the cookie-app job. It adds passkeys, step-up ReAuth, composable modules, and hardening defaults: rate limits, antiforgery, lockout, and refresh-token reuse detection. Use `MapIdentityApi` if the framework sample is enough. Use AuthEndpoints if you need cookies, passkeys, or to compose only the routes you need.

The next sections list where `MapIdentityApi` stops. [Shared routes side by side](#shared-routes-side-by-side) compares register, login, password reset, and two-factor authentication route by route.

## What MapIdentityApi maps

`MapIdentityApi<TUser>()` is ASP.NET Core's Identity API. One call maps register, login, refresh, email confirmation, password reset, and account management onto your Identity user store. AuthEndpoints uses that same store. The sections below list where `MapIdentityApi` stops in .NET 10, and which AuthEndpoints call covers each gap.

In .NET 10, `MapIdentityApi<TUser>()` maps this set. Paths sit at the app root unless you wrap the call in `MapGroup`.

| Method | Path |
| --- | --- |
| `POST` | `/register` |
| `POST` | `/login` |
| `POST` | `/refresh` |
| `GET` | `/confirmEmail` |
| `POST` | `/resendConfirmationEmail` |
| `POST` | `/forgotPassword` |
| `POST` | `/resetPassword` |
| `POST` | `/manage/2fa` |
| `GET` | `/manage/info` |
| `POST` | `/manage/info` |

```cs
builder.Services
    .AddIdentityApiEndpoints<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>();

app.MapGroup("/identity").MapIdentityApi<AppUser>();
```

`POST /login` uses the Identity bearer scheme unless the query string sets `useCookies` or `useSessionCookies`, which issue the application cookie instead. Request bodies are the Identity types (`RegisterRequest`, `LoginRequest`, and the rest). There is no `GET /manage/2fa`. The method's documentation comment mentions logging out. The method does not map a logout route.

## Logout

`MapIdentityApi` has no logout route. The [Identity API authorization](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0) article tells you to add your own `POST /logout` that calls `SignInManager.SignOutAsync()`. That signs out the application scheme, plus the external and two-factor user-id schemes when they are registered. It does not sign out the two-factor remember-client cookie. It does not revoke bearer tokens. The bearer handler treats sign-out as a no-op, so the access token and the refresh token stay valid until they expire.

AuthEndpoints maps a logout route on each sign-in stack. Each stack ends a different thing. Client steps: [Sign users out](/guides/sign-out).

| Stack | Route | What logout ends |
| --- | --- | --- |
| Cookie (facade default) | `POST /identity/logout` | Application, external, two-factor user-id, remember-client, and ReAuth cookies. Requires a signed-in user and a CSRF token. |
| Identity bearer | `POST /identity/logout` | Those same cookies. Bearer access and refresh tokens stay valid until they expire. Requires a signed-in user. No CSRF token. |
| JWT | `POST /auth/logout` | The refresh-token family for the refresh cookie, and the cookie itself. The access JWT stays valid until it expires (15 minutes by default). CSRF token required. A signed-in user is not required. |

Cookie logout:

```js
const { csrfToken } = await fetch('/identity/csrfToken', { credentials: 'include' }).then(r => r.json());
await fetch('/identity/logout', {
  method: 'POST',
  credentials: 'include',
  headers: { 'RequestVerificationToken': csrfToken }
});
```

`GET /identity/csrfToken` is part of the cookie module. `MapIdentityApi` does not map it.

## Choose which endpoints to map

`MapIdentityApi` maps the full table above in one call. `MapGroup("/identity")` prefixes every route with `/identity`. The builder it returns can add conventions to that group. It has no parameter that omits `/register`, and no parameter that renames `/login`.

AuthEndpoints splits the same jobs into modules. Map the ones you need:

| Module | What it adds |
| --- | --- |
| `MapIdentityManagementApi` | Register, confirm email, resend, forgot/reset password, manage info, set password, 2FA, ReAuth |
| `MapPasswordEndpoints` | Register, forgot/reset password, and login for cookie or Identity bearer. `PasswordLoginMode.None` omits login. |
| `MapConfirmEmailEndpoints` | `GET /confirmEmail` and `POST /resendConfirmationEmail`, once per endpoint name |
| `MapAccountManagementEndpoints` | Manage info, set password, 2FA, auth methods, and `POST /confirmIdentity` |
| `MapCookieAuthEndpoints` | Cookie `POST /login`, `POST /logout`, `GET /csrfToken` |
| `MapCookieSessionEndpoints` | Cookie `POST /logout` and `GET /csrfToken` |
| `MapBearerAuthEndpoints` | Identity bearer `POST /login`, `POST /refresh`, `POST /logout` |
| `MapBearerSessionEndpoints` | Identity bearer `POST /refresh` and `POST /logout` |
| `MapJwtAuthEndpoints` | JWT `POST /create`, `POST /refresh`, `GET /verify`, `POST /logout`, `GET /csrfToken` |
| `MapJwtPasswordEndpoints` | JWT `POST /create` |
| `MapJwtSessionEndpoints` | JWT refresh, verify, logout, and CSRF token |
| `MapPasskeyEndpoints` | Passkey register, login, and credential management |
| `MapPasskeySignInEndpoints` | Passkey register and login, plus confirm-email on the parent group when that name is new |
| `MapPasskeyManagementEndpoints` | Signed-in passkey list, add, rename, and delete |

The 3.x facade (`MapAuthEndpoints`) is one composition: management plus either cookie or Identity bearer sign-in under `IdentityPath` (default `/identity`). Passkeys are on by default under `PasskeyPath` (default `/account`). JWT is off until `Jwt.Enabled` is true.

This maps management and cookie sign-in under `/api/account`, with passkeys and JWT left off:

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(o =>
{
    o.IdentityPath = "/api/account";
    o.Passkeys.Enabled = false;
});
builder.Services.AddTransient<IEmailSender<AppUser>, MyEmailSender>();

var app = builder.Build();
app.UseAuthEndpoints();
app.MapAuthEndpoints<AppUser>();
```

`POST /api/account/login` on that host is cookie login. The relative names stay `/login`, `/register`, and `/logout`. AuthEndpoints does not rename those segments. `MapIdentityManagementApi` always includes `/register`. `MapCookieAuthEndpoints` always includes `/login`. The smaller maps omit a piece: `MapPasswordEndpoints` with `PasswordLoginMode.None` skips `/login`, and `MapCookieSessionEndpoints` maps logout and the CSRF token. An email-code host uses those pieces. See [Email-code only](/composables#email-code-only).

To skip cookie login and map JWT instead, compose the modules. Register the matching services first, call `modelBuilder.UseRefreshToken()` on the `DbContext`, and migrate. The route map is:

```cs
app.MapGroup("/account").MapIdentityManagementApi<AppUser>();
app.MapGroup("/auth").MapJwtAuthEndpoints<AppUser>();
```

Full host setup: [Build a custom auth stack](/composables#copy-a-host). Prefix reference: [Configuration options](/modules/configuration).

## JWT, opaque bearer tokens, and cookies

`MapIdentityApi` login without `useCookies` or `useSessionCookies` returns Identity bearer tokens (`accessToken`, `refreshToken`, `expiresIn`, `tokenType`). Those values are data-protection tickets (`BearerTokenProtector` and `RefreshTokenProtector`), not JWTs. Microsoft's Identity API article states that the tokens are not standard JSON Web Tokens. Another service validates them with the Identity bearer handler and the same data-protection keys. `JwtBearer` and a signing key do not validate them. `?useCookies=true` or `?useSessionCookies=true` on that same `/login` issues the application cookie and does not return a token body.

AuthEndpoints has three password sign-in stacks. Identity bearer is the same ticket format as `MapIdentityApi`. JWT is a separate opt-in.

| Stack | What login returns | Refresh |
| --- | --- | --- |
| Cookie (facade default) | Application cookie. Empty body. | The browser sends the cookie. |
| Identity bearer | Opaque `accessToken` and `refreshToken` in the body | `POST /identity/refresh` with `{ "refreshToken" }` |
| JWT | JWT `accessToken` in the body, refresh token in the `AuthEndpoints.Jwt.RefreshToken` cookie | `POST /auth/refresh` with that cookie and a CSRF token. The stored token is a hash. Each refresh rotates it. Reuse of an old token revokes the family. |

On the 3.x cookie facade, `POST /identity/login` always uses the application cookie. `useCookies` is ignored there. A persistent cookie is `?useSessionCookies=false`. The flag table for Identity bearer login matches `MapIdentityApi`. The password facade uses `/auth` and the same cookie rule. Details: [Choose your sign-in setup](/getting-started/choose-a-sign-in-stack) and [Shared routes side by side](#shared-routes-side-by-side).

Turn JWT on beside the cookie facade. You still call `modelBuilder.UseRefreshToken()` and add a migration:

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(o =>
{
    o.Passkeys.ServerDomain = "example.com"; // required in Production while passkeys stay on
    o.Jwt.Enabled = true;
    o.Jwt.Configure = jwt =>
    {
        jwt.Issuer = "https://example.com";
        jwt.Audience = "https://example.com";
        jwt.SigningOptions.SymmetricKey = builder.Configuration["Jwt:SymmetricKey"];
    };
});
```

`MapAuthEndpoints` then also maps `/auth/create`, `/auth/refresh`, `/auth/verify`, `/auth/logout`, and `/auth/csrfToken`. Signing keys, algorithms, and lifetimes: [JWT module](/modules/jwt).

## Passkeys

`MapIdentityApi` does not map passkey routes. The .NET 10 Blazor Identity template has passkey pages, and its `MapAdditionalIdentityEndpoints` posts to `/Account/PasskeyCreationOptions` and `/Account/PasskeyRequestOptions`. Those routes belong to that template. They are not `MapIdentityApi`, and they are not a passkey register, login, and credential API for a separate client.

AuthEndpoints maps that API. The 3.x facade turns it on by default under `{PasskeyPath}/passkeys` (`/account/passkeys`). In Production set `Passkeys.ServerDomain`, or set `Passkeys.Enabled` to false to skip passkey services and routes. The password facade maps passkeys only when `Passkeys.ServerDomain` is set, under `/auth/passkeys`. See [Choose your sign-in setup](/getting-started/choose-a-sign-in-stack).

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(o =>
{
    o.Passkeys.ServerDomain = "example.com";
});
```

Mapped routes include `POST /account/passkeys/register`, `POST /account/passkeys/login`, `GET /account/passkeys/`, and add, rename, and delete. Passkey sign-in skips two-factor authentication. With no session argument, the completer follows Identity bearer query flags (`useCookies` or `useSessionCookies`), not cookie-facade `LoginCookie`. Pass `AuthEndpointsSession.Jwt` when passkey sign-in should issue a JWT. Route table and ceremony: [Passkeys module](/modules/passkeys). Client steps: [Register users](/guides/registration#register-with-a-passkey) and [Sign users in](/guides/sign-in#sign-in-with-a-passkey).

## When MapIdentityApi is enough

Use `MapIdentityApi` when its ten routes, and a logout handler you write, cover the app. Use AuthEndpoints when you need a logout route, a prefix with only some modules, a JWT access token, or passkey endpoints.

## Shared routes side by side

Both stacks sit on ASP.NET Core Identity and your EF user store. **Stock** here means Microsoft's Identity API endpoints (`AddIdentityApiEndpoints` and `MapIdentityApi`) or the same routes written by hand. **AuthEndpoints** in the tables means the 3.x cookie facade: `AddAuthEndpoints`, `UseAuthEndpoints`, and `MapAuthEndpoints`. The password facade (`AddPasswordAuth` and `MapPasswordAuth`) uses the prefix `/auth` and leaves passkeys off until `Passkeys.ServerDomain` is set.

This section compares the routes that both stacks share.

Request bodies stay Identity-shaped (`RegisterRequest`, `LoginRequest`, `ForgotPasswordRequest`, `ResetPasswordRequest`, `TwoFactorRequest`). AuthEndpoints maps the routes and adds cookie login, CSRF where required, rate limits, and ReAuth. It does not invent alternate DTOs.

AuthEndpoints tables use the facade default prefix `/identity` (`IdentityPath`). Stock `MapIdentityApi` has **no** built-in prefix unless the host wraps it in `MapGroup`.

AuthEndpoints-only on this surface: `GET /identity/csrfToken`, cookie `POST /identity/logout`, and ReAuth (`/manage/authMethods`, `/confirmIdentity`). Stock `MapIdentityApi` does not map logout.

Client steps for these flows are in [Guides](/guides).

### Host setup

#### Stock (`MapIdentityApi`)

```cs
builder.Services
    .AddIdentityApiEndpoints<AppUser>()
    .AddEntityFrameworkStores<AppDbContext>();

var app = builder.Build();

// Optional prefix — without MapGroup, routes are at the app root (/register, /login, …).
app.MapGroup("/identity").MapIdentityApi<AppUser>();
```

You still wire authentication, authorization, antiforgery, CORS, and rate limiting yourself. Login is bearer-first unless the client passes cookie query flags.

#### AuthEndpoints (cookie facade)

```cs
builder.Services.AddAuthEndpoints<AppUser, AppDbContext>(o =>
{
    o.Passkeys.Enabled = false; // thin cookie path; omit or set ServerDomain when passkeys stay on
    o.Jwt.Enabled = false;
});
builder.Services.AddTransient<IEmailSender<AppUser>, MyEmailSender>();

var app = builder.Build();

app.UseAuthEndpoints(); // authentication, authorization, rate limiting, antiforgery
app.MapAuthEndpoints<AppUser>();
```

Passkeys and JWT are off. When you leave passkeys enabled (facade default), set `Passkeys.ServerDomain` in Production. See [Quick start](/getting-started/quick-start).

CSRF on the AuthEndpoints cookie stack applies to cookie **logout**, **manage** POSTs, **ReAuth**, authenticated **resendConfirmationEmail**, and every passkey route except the list. It does **not** apply to register, login, forgotPassword, or resetPassword. See [Antiforgery (CSRF) rules](/modules/csrf).

### Register

| | Stock Identity API | AuthEndpoints facade |
| --- | --- | --- |
| Route | `POST /register` (or `POST /identity/register` with `MapGroup`) | `POST /identity/register` |
| Body | Identity register (`email`, `password`) | Same Identity body |
| CSRF | Host policy (endpoint does not require antiforgery by default) | **Not** required (`RequireAntiforgery` is not on register) |
| Duplicate email | `200` (no enumeration) | `200` (no enumeration) |
| Confirmed-account policy | Host Identity options | `RequireConfirmedAccount` default `true` |
| After `200` | Not signed in | Not signed in (`200` ≠ session) |
| Confirm | `GET …/confirmEmail?userId&code` | `GET /identity/confirmEmail?userId&code`, then login. Optional `ConfirmEmailRedirectUri` → `302` with `status` / `flow` |
| Rate limit | Host-owned | Built-in account rate limits |

Client flow: register → check email → confirm → login. Steps: [Register users](/guides/registration).

### Login

| | Stock Identity API | AuthEndpoints facade |
| --- | --- | --- |
| Route | `POST /login` (or under your `MapGroup`) | `POST /identity/login` |
| Handler | Identity `Login` | `LoginCookie` |
| Body | Identity `LoginRequest` | Same (`email`, `password`, optional 2FA fields) |
| Default success | Identity bearer tokens (`AccessTokenResponse`) | Application cookie only (no bearer): empty body + `Set-Cookie` (`TypedResults.Empty`). Session when the flag is omitted |
| Cookie query flags | `useCookies` / `useSessionCookies` select cookie vs bearer | **Only** `useSessionCookies` (`useCookies` ignored). Persistent: `?useSessionCookies=false` |
| CSRF on login | Not required | Not required |
| Logout | Not in `MapIdentityApi` | `POST /identity/logout` (auth + CSRF) |
| CSRF helper | Host-owned | `GET /identity/csrfToken` for logout, manage, ReAuth, resend |
| Lockout | Identity lockout | Lockout + login rate limit |

Full flag tables: [Cookie auth](/modules/cookie-auth). Bearer-style Identity login stays available via compose (`MapBearerAuthEndpoints`) or `SignIn = IdentityBearer`. It is not the cookie-facade default.

### Password reset

| | Stock Identity API | AuthEndpoints facade |
| --- | --- | --- |
| Forgot | `POST …/forgotPassword` `{ email }` → always `200` | `POST /identity/forgotPassword` → always `200` |
| CSRF / session on forgot | Not required | Not required |
| Mail | Your `IEmailSender<TUser>` | Same (Production rejects Identity's no-op sender) |
| Reset code | From mail | Base64Url token from the sender; send that value as `resetCode` |
| Reset | `POST …/resetPassword` `{ email, resetCode, newPassword }` | Same Identity body on `/identity/resetPassword` |
| CSRF / session on reset | Not required | Not required |
| Then | `POST …/login` | `POST /identity/login` (`LoginCookie`) |

Client steps: [Reset a forgotten password](/guides/reset-password).

### Two-factor authentication

| | Stock Identity API | AuthEndpoints facade |
| --- | --- | --- |
| Status | *No GET* — use `POST /identity/manage/2fa` (response includes `sharedKey` / flags) | `GET /identity/manage/2fa` → `isTwoFactorEnabled` only |
| Shared key | On stock POST response (`TwoFactorResponse.sharedKey`) | Mint/read via `POST /identity/manage/2fa` + `{}` (not GET); CSRF + ReAuth |
| Enable / disable | Auth’d `POST /manage/2fa` (`TwoFactorRequest`) | Auth’d `POST /identity/manage/2fa` (same Identity body); CSRF + ReAuth |
| CSRF on `POST` | Not required by `MapIdentityApi` | Required (`RequestVerificationToken`) |
| Step-up | Not built in | ReAuth required (`confirmIdentity`, then cookie or `X-AuthEndpoints-Reauth`) |
| `enable` + `resetSharedKey` | Avoid together | Do not send together (validation problem) |
| Login with 2FA | `twoFactorCode` / `twoFactorRecoveryCode` on `Login` | Same fields on `LoginCookie` |

Client steps: [Turn on two-factor authentication](/guides/two-factor) and [Require step-up before sensitive actions](/guides/step-up).

### After these four flows

AuthEndpoints also maps manage info, ReAuth routes, and optional passkeys/JWT. Stock `MapIdentityApi` does not include passkeys, ReAuth, cookie logout, or `csrfToken`. Those gaps are covered in [What MapIdentityApi maps](#what-mapidentityapi-maps) and the sections after it. Compose only the modules you need when the facade is too much. See [Build a custom auth stack](/composables) and [Identity management module](/modules/identity-management).
